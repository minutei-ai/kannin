# Architecture and completion gates

Kannin is a separate OSS repository. No Minutei production data, fixtures, secrets, or services are bundled.

## Ownership

The Worker authenticates every namespace operation. Writes and default strong reads route to one volatile Durable Object coordinator. Explicit edge-eventual text reads select a bounded-age R2 snapshot and run the same Rust scorer in the edge Worker. If acquisition returns a snapshot outside that age budget or below the requested sequence, the original authenticated request routes to the coordinator, which validates the sequence against its current view. Expired snapshots never participate in ranking. Canonical edge snapshot acquisition has a nominal 900 ms shared budget. Readers joining the same in-flight root reuse its original outcome rather than starting another budget. A timeout or a full sixty-four-entry pending table recovers through the coordinator and reports `edge_snapshot_r2_timeout` or `edge_snapshot_r2_admission`. The original acquisition remains in `waitUntil` until its native body read settles; fully validated late bodies may enter the bounded memory cache only as expired payload/ETag candidates. They cannot serve queries or enter Cache API publication until a fresh canonical R2 read confirms their version. `snapshotLateRetentions` counts admitted candidates; it does not count cache publication or prove a latency improvement. A separate semaphore charges body acquisition and Schema decoding at four times object size, in 64 KiB units against a four-MiB target; an oversized individual body consumes every permit. Body admission never queues: a busy budget cancels the unused body and recovers through the coordinator with `edge_snapshot_r2_body_admission`. Headers arriving after the age budget may still consume and validate their body under the same admission quota when the object fits the candidate cache; oversized late headers and backwards-clock observations cancel their unread body. This can consume an additional late body read, but allows a later conditional R2 read to avoid downloading an unchanged manifest again. These quotas do not bound the whole Worker heap or guarantee native timer scheduling. This recovery can add the coordinator's network hop; its response carries request-local `edge_snapshot_fallback` timing. Canonical decoding/storage failures still fail, and an uncommitted future sequence still returns 409. Each object serializes mutations and strong-read manifest capture with an instance-owned Effect semaphore. Up to four strong queries run outside that semaphore after capturing an immutable root; queued readers capture only after admission. A read therefore observes its captured sequence even when a later reset or compaction commits. In-flight reader leases pin their segments during collection and release on success or failure. Collection rejects more than 16,384 unique references before deleting segments. Query failures do not clear concurrent writer state. Failure responses retain completed query timings and request-local `text_phase` markers for catalog, ranking, document acquisition or a shared producer wait. These markers identify entered phases and do not establish CPU time. Worker timers advance only after I/O, so synchronous WASM phases can report zero despite consuming CPU; CPU profiles remain necessary for synchronous cost attribution. Response timings separate admission/coordinator wait (`query_wait`) from canonical root acquisition (`query_root`); neither establishes CPU use or network placement. Concurrent namespaces remain independent. The application never calls `ctx.storage` and never opens a local database. The coordinator caches the R2 manifest; all searchable data and recovery state belong to R2. Rust/WASM owns immutable index construction, positional postings, field-normalized BM25, exact block-bound pruning, filters, log compression, integrity checks and the shared text normalization used for both indexing and queries.

Benchmark samples retain `cf-placement` separately from ingress `CF-Ray`. The owning Alchemy Worker enables Smart Placement with `placement: { mode: "smart" }`. Cloudflare may relocate the default HTTP fetch handler after observing traffic; named catalog/segment entrypoints and Durable Objects retain their native placement contracts. The initial native experiment showed no relocation or latency improvement. Enabling the setting again does not establish a latency gain; comparisons must retain placement observations and native timings. See [Cloudflare placement](https://developers.cloudflare.com/workers/configuration/placement/).

Cloudflare's current [Durable Object location contract](https://developers.cloudflare.com/durable-objects/reference/data-location/) does not relocate existing objects when a hint changes. Its South America hint currently places objects in Eastern North America. Adding a `sam` hint therefore cannot remove the existing coordinator's international hop. Strong reads retain the coordinator contract; changing routing or replacing a coordinator requires separate correctness and native latency evidence.

Each coordinator also owns active text evaluations keyed by the captured manifest object and the complete Schema-encoded request, including text, match mode, top-k, filters, consistency and sequence barrier. Identical admitted text requests share the producer's row Promise while it runs. Each caller retains its own read lease, response encoding, sequence check and timings. Success and failure remove the entry; no completed query result is retained. Distinct roots, including same-sequence compaction, cannot join, and namespace ownership follows the coordinator instance. The existing four read slots bound active entries and retained request keys; these transient values are outside the immutable-cache quotas and do not establish peak-memory bounds. Followers report `text_inflight` wait time. Edge execution and vector/hybrid provider operations do not use this coordination.

Snapshot Cache API acquisition has a 250 ms foreground budget, including opening, matching and decoding. Concurrent readers with the same bucket, namespace and minimum sequence share that budgeted lookup until the underlying operation settles. A timeout uses canonical R2 and reports `edge_snapshot_cache_timeout`; `waitUntil` retains the outstanding native lookup. Late cache bodies must still pass the age and sequence checks, and cannot replace a newer sequence or a newer observation of the same sequence in memory. Background refresh after 250 ms of snapshot age remains independent of this lookup budget.

The internal snapshot Cache API namespace uses a versioned binary frame: eight magic bytes, a little-endian metadata length, a Schema-encoded observation timestamp/sequence and retained manifest JSON bytes. Canonical R2 stays at its existing format. A fresh R2 body is decoded and validated once, retaining its original UTF-8 bytes for the frame instead of reserializing the complete manifest. An unchanged conditional R2 ETag reuses both the decoded manifest and retained payload. A retained per-entry timestamp groups Cache API publication attempts within 500 ms only for unchanged ETags; changed bodies publish immediately. Suppressed publications neither build a full payload Blob nor rewrite an older cached frame's observation time. Memory snapshots still use their own new canonical observation; every reader enforces the same one-second age and sequence barrier. Cache eviction or unsuccessful publication can leave other isolates with a miss until the next attempt; those readers recover through R2. Health reports isolate-local publication attempts, offered frame bytes and skipped publications, not storage receipts or billed usage. Cache readers validate framing, metadata, canonical Root Schema, matching sequences and body age; HTTP metadata only rejects ineligible bodies before decoding. Corruption recovers through R2. The cache cutover uses one new namespace without a legacy reader. The 24 MiB process LRU charges four times the larger of frame size and retained backing-buffer size, including payload views into a complete frame. Health reports charged bytes and retained payload buffers separately; these counters do not establish total Worker peak memory.

R2 owns canonical mutation logs, receipts, index segments and the atomic root. A write's sequence is assigned by the namespace coordinator. The segment and log are prepared before I/O and stored concurrently under separate immutable object keys. Both writes must complete successfully before a conditional root update. The root, rather than object listing, defines which documents committed. Receipt acknowledgement and queue submission follow that commit. Receipts use a conditional create; a collision reads and validates the existing receipt. The coordinator remembers only its last confirmed receipt to avoid repairing that same acknowledgement before every warm write. Losing this memory restores the canonical R2 repair path. A request may fail after committing in R2; retry the same request id and payload. The manifest retains the last receipt so an interrupted receipt write can be repaired before another mutation. Logs and idempotency receipts are retained indefinitely. Collection never deletes them, so request-id reuse keeps its original conflict/idempotency behavior; operators must budget this retained history.

Canonical header parsing validates UTF-8 before the native JSON string reader; framing, CRC and structural checks remain required. The WASM target enables `simd128` through the owning Cargo target configuration, and miniz uses its native SIMD Adler-32 backend. Internal directory acquisition uses the immutable `/directory-v2` cache resource and `RAIODIR2` frames. Rust validates the complete canonical header before serializing its native fields as compact JSON sequences, retaining dictionary keys and the original raw attribute JSON. Serde decodes those sequences directly into the existing Header, DocumentMeta, TermMeta, BlockMeta and Range contracts; there is no second domain model. The twenty-byte frame prefix carries magic, canonical header length, compact decoded length and CRC. The CRC covers the first sixteen frame bytes and the decoded compact payload, protecting both declared lengths as well as content. Decoding checks the requested canonical length, caps the compact body at sixteen MiB, validates zlib integrity and CRC, rejects trailing JSON and applies the same header version, document ordering, frequency and block-directory validation as canonical reads. Rust retains immutable term entries in a sorted boxed slice and uses exact binary search for lookup. Stable sorting and explicit last-value deduplication preserve JSON-map semantics for unordered and escaped duplicate keys; canonical and compressed serialization retain the same order and bytes. Validated document vectors release unused capacity before admission. Directory charging accounts for the retained slice, strings, blocks and document capacity against the existing quota. Smaller retained headers can admit more directories, but do not imply a lower WASM linear-memory high-water mark or whole-Worker peak. The cache cutover uses the new private HTTP path and R2 prefix without reading old frames; a missing or invalid artifact is rebuilt from the unchanged canonical header. R2 segment bytes and posting/document offsets are unchanged. Encoded directories have an eighteen-MiB pool: seventeen MiB for charged frames and one MiB for bounded access counters. One MiB holds learned segment score bounds and another MiB holds compact text plans. Decoded-directory admission is twenty MiB, and raw ranges/frequency pages retain twelve MiB, keeping these cache quotas at fifty-two MiB total. The forty-MiB individual decoded-directory validation limit remains; larger-than-admission directories remain scoped and uncached. Both encoded and decoded directory admission displace resident entries only when the incoming access count exceeds every required LRU victim count. Decoded hits advance the same bounded history as encoded-directory accesses. Counts saturate at 255 and halve every 4,096 directory accesses; cold counter entries disappear, and namespace invalidation clears retained entries and history. Up to sixty-four active source/header identities separately retain validated Rust handles while readers use them, including when cache admission rejects the object. A scoped SHA-256 fingerprint permits an identical copied frame to reuse that validated handle without parsing its JSON again. Both fingerprint and handle are released with the last reader. Concurrent readers share those handles; the last reader releases the temporary reference on completion or failure. A full active table keeps the ordinary acquisition path. These temporary handles have request lifetimes and do not extend cache retention or carry root, authorization or query-result authority. Raw buffer charges include keys/entry overhead, while payload bytes remain separately reported. These are cache quotas, not a bound on active rankers, transient decoding or complete Worker peak memory. Cache identities keep the bucket/object prefix used by namespace invalidation, with a format suffix separating compressed directories from raw ranges. Document-range batching still tests raw-range identities, and in-flight acquisition sharing remains format-specific. Uncompressed ranges of at most 64 KiB give the complete cached binding fetch, including its body, a nominal 250 ms budget. Timeout sends an abort signal to that fetch and reads the same immutable range directly from canonical R2. A semaphore charges eligible acquisitions at four times requested bytes, rounded to 64 KiB units, against four MiB. Canonical fallback body reads settle before releasing permits; unused R2 bodies are canceled. The existing same-range Promise sharing covers both paths. Small-range quota admission uses nonqueued permits and one-millisecond native timer retries, preserving the original wait-for-capacity behavior and four-MiB charge without waiting on a foreign invocation's semaphore callback alone. Compressed directories and larger ranges keep the cached binding path without this fallback. Cache failures and invalid response lengths remain failures rather than timeout recovery. Health and metadata count timeout events, direct fallback attempts and transferred fallback bytes per isolate; these counters do not establish billed origin reads or total peak memory. Cancellation does not guarantee that a remote cache origin stopped an already-started read, so fallback may add an R2 request. Cache API and Worker Cache retain this derived representation without query-selector keys. Each immutable segment has a versioned, CRC-checked header and independently compressed, length-bounded, CRC-checked document/posting pages. Postings encode local row ids, title/body term frequencies and token positions with delta varints. Any/all scoring stores compact row/title-frequency/body-frequency lists; phrase scoring retains positional lists. Both readers validate every varint, including position ordering/overflow, CRC, decoded length and document-position bounds. After validating every decoded posting, the scorer retains only rows allowed by filters and tombstones. A separate per-term last-decoded-row map preserves block-order validation even when excluded rows are discarded. New filter masks retain only attributes named by their filters; small-field overview projections use the same reader. Unused JSON values are traversed without constructing value trees, while preserving number, string, nested structure and recursion validation. Cached masks remain keyed by the complete filter and tombstones remain query-local. Full term catalogs still supply global statistics and conservative score bounds. The shared scoring/cursor algorithm is monomorphized for each list representation, with no per-row dynamic dispatch. A lazy, request-local Rust PreparedQuery parses shared ranking input, normalizes words, sorts and deduplicates term indices, compiles BM25 scorers and records repeated-token phrase order once. Segment rankers share that immutable preparation; each selected segment still applies its own filters and tombstones. Its constructor requires an empty shared dead-row list, and the segment ranker receives the actual list separately. Native DisposableStack lifetime releases the plan on completion/error, while rankers retain the reference-counted immutable term preparation and remain valid after plan release. The plan retains normalized words, statistics, sorted indices, scorers, phrase order, mode, top-k and filters; original query text and the empty shared tombstone vector are released after validation. Segment eligibility and posting lists remain independently owned. No compiled query enters a process cache. Top-k scoring reserves its bounded heap once and replaces the worst hit only when a candidate wins the existing score/row comparison. Noncompetitive candidates do not enter the heap; the heap never needs a transient k-plus-one hit. Search list storage is internal; Rust callers use `Search::add` and `Search::finish` rather than the former public `lists` field. The persisted posting layout and HTTP contract are unchanged. A block directory stores ranges and conservative frequency/length bounds. R2 range reads fetch only needed posting pages and result documents. The Rust ranker emits each winning row's existing document byte range while its validated header remains retained. Global top-k merges keep that range with its segment and score; materialization reads those pages directly, without reopening the directory or crossing a second JSON/WASM range-projection boundary. Reading a document refreshes an already-resident directory's LRU position without decoding or retaining an absent header. Each text or vector materialization branch shares eight document read permits when all selected encoded frames total at most 64 KiB; larger selections retain four. Hybrid evaluation can execute both branches concurrently. This bounds the widened branch by the entire encoded selection, not by one page, and does not bound decoded response size or whole-Worker heap. Ranking and vector reconciliation retain their existing four-reader limits. Canonical range checks, CRC and StoredDocument Schema remain in force. Up to four consecutive physical rows from the same immutable segment may share a read of at most 1 MiB, without gaps or overfetch. Page references are sorted only to select that range; decoding and returned rows preserve the original ranking order. Text, vector and hybrid materialization use this acquisition policy, with sparse rows and mixed segments retaining individual reads. A query-local semaphore bounds directory, document and related I/O to four operations. Header acquisition and posting ranges share four permits; decoded rankers are released at the window boundary. Each window merges its bounded top-k before selecting the next. An older cutoff can cause extra reads but cannot exclude a winning row. Preparation/acquisition timing counters sum segment intervals and may exceed the overlapping ranking wall time. Before posting acquisition, the Rust ranker omits blocks whose complete row interval is excluded by filters or tombstones. Once earlier segments supply a full global top-k, it also omits pages whose conservative complete-query score bound cannot beat that cutoff. The bound sums each term's maximum block score across overlapping row intervals, using live global statistics and sorted-term addition. Equality pruning compares the first eligible document identifier in UTF-16 order; the existing strict-score tolerance remains unchanged. Competitive rows retain all contributing term pages. The original span builder regroups retained pages within the same gap/length budgets; the first segment still has no global cutoff. Without one, any/all may derive a local lower cutoff from terms present in every physical document. It evaluates a minimum one-occurrence score across legal nonempty fields for currently eligible rows, retaining a bounded top-k heap. Page upper bounds use the minimum title/body lengths among currently eligible rows in each term block, clamped against that block's original physical minima. A block with no eligible row contributes zero; unrestricted masks use the original physical bounds. The same query-local bounds serve acquisition and finish-time pruning, with no persistent mask-derived metadata. Any needs at least one such term, all needs every requested term, and phrase keeps the original path. This cutoff includes its own kth identifier because its supporting rows have not yet entered the final ranking; insufficient positive eligible rows use the original spans. Remaining blocks share a span when each excluded byte gap is at most 4 KiB; larger gaps split the span. Only selected pages are decoded, and each retains CRC and token-position validation. Spans remain bounded to the segment size and reads run in windows of four. Global document frequencies and score bounds still use the complete immutable term catalog. Every document page retains its own CRC and Schema validation; copied page buffers are separately charged to the existing range LRU so subset queries can hit memory without retaining an uncharged larger backing buffer. The native shared cache retains merged ranges. A different subrange after memory eviction may miss those entries and fall back to R2. Concurrent readers of the same bucket/object/offset/length additionally share one pending native acquisition per isolate. Its owner consumes the response body and validates its length before resolving immutable bytes; responses, readers and Effect fibers are never shared. Success and failure remove the entry. The pending map tracks at most 64 acquisitions and bypasses tracking at capacity. A shared process-owned LRU retains immutable range bytes and decoded Rust frequency pages within the same 12 MiB budget. Any/all pages with repeated title/body occurrences may retain checked rows, counts and final positions; phrase and single-occurrence pages use the original decoder. Cache admission validates compression, CRC, lengths, every varint and position ordering once. Every ranker attachment still checks document/position bounds, block order, filters and current tombstones. Physical bucket/object/offset/length identifies each immutable page; eviction and namespace clearing release its WASM handle. Metadata and health expose raw rangeCacheBytes and conservatively charged postingCacheBytes separately. Compressed range acquisition still occurs before attachment; this cache avoids repeated decoding rather than origin reads. Decoded Rust directories have a separate 20 MiB conservatively charged admission budget and a 40 MiB individual validation ceiling and deterministic reference-counted leases; retained Rust Bloom batches have a 4 MiB charged budget including bitsets, offsets, cache keys and prefix metadata. Query-selected immutable term catalogs have a separate 4 MiB conservatively charged LRU. All storage caches use the physical bucket name and immutable object version, so distinct native binding references to the same bucket share entries. Each directory includes a conservatively charged 32 KiB filter-mask budget, capped at 16 entries; masks derive solely from immutable attributes, and tombstones apply on a query-local copy. Filter-aware segment score bounds use minimum eligible field lengths without weakening exact ranking. Rust retains a query-local block-bound cursor per term after top-k fills; postings advance monotonically, so a binary search is needed only when the current bound no longer covers the posting row. Segment parsing rejects reordered or overlapping posting block row intervals. Score arithmetic, pruning tolerance and tie order remain unchanged. These caches are disposable. Blooms in the root prune unrelated segment reads. Probe inputs and hashes are shared across batches of at most 64 bitsets, with bounded packed buffers and checked offset framing. Immutable batches retain their bytes inside WASM so cache hits avoid JavaScript repacking and host-to-WASM byte transfer. Identity includes physical bucket, Bloom field and ordered immutable segment keys, preserving reuse after manifest rehydration. Eviction and namespace rebuild free native handles; oversized batches bypass retention with scoped release. Document reconciliation visits aligned sixty-four-segment windows newest first, including a partial newest window, then reverses matches within each window. It removes IDs already resolved and retains exact lookup/tombstone checks. For `all` and phrase queries, a negative Bloom intersection across every segment returns empty before acquiring directories. When an intersection remains possible, all candidate dictionaries still contribute global document frequencies; segments missing a required live term are then skipped before posting reads. Bloom false positives can add work but cannot remove valid matches. Tombstoned rows and per-segment removed document frequencies keep namespace-wide scoring correct across updates and deletions.

Recovery loads the root and its referenced index objects; it does not replay a database or require the log to construct a hot index. Losing all coordinator memory therefore preserves committed state. Native Cloudflare Queues schedule bounded compaction; explicit compaction also builds a new immutable segment from live records and activates it with root CAS. Original document revisions, attributes, vectors and global statistics survive physical moves. The explicit paginated collector quarantines superseded and orphan segments before physical deletion. CRC32 detects accidental corruption; bucket authorization, rather than CRC32, controls who may modify canonical objects.

Vectorize owns the ANN index. Native Cache API retains successful nonempty candidate lists in versioned frames carrying the observation time from before the provider call. HTTP retention is two seconds, while every reader independently requires an observation younger than one second and rejects future timestamps. Delayed publication cannot renew that observation. Its internal key includes the physical bucket, namespace epoch, canonical sequence, pending vector jobs, vector, filters and indexed-field configuration. Writes, resets and outbox transitions therefore select different keys. Cache misses, expiry, invalid cached data and cache unavailability use the native provider; empty lists and failures are never stored. Provider visibility remains eventual and a cached list can add up to one second before an asynchronous index change is observed. Every cache hit still acquires the current strong R2 view through the coordinator and reconciles candidates before materialization; document or query-result authority is never cached. Request-local `vector_cache` timing labels distinguish hit and miss; `vector_cache_rejected` identifies an invalid age. Optional publication runs through native `waitUntil`, outside row delivery, with `vector_publish_scheduled` or `vector_publish_skipped` admission markers. Neither marker proves storage success. The `vector_index` interval includes cache selection and provider acquisition, not background publication. Query candidates are reconciled with the current R2 root in ordered windows before document materialization. Each window covers the remaining requested count, with a minimum of four candidates; processing stops once enough live eligible candidates are found or the provider list ends. All provider metadata is decoded at its boundary, and skipped stale/residual-filter candidates allow later windows to run. Revision-specific ids, vector presence and residual filters are checked with concurrency four; only the first requested top-k eligible candidates load document pages, also with concurrency four and provider order preserved. Filters are encoded once. Empty canonical namespaces avoid provider calls after input validation. Hybrid lexical and vector reads start concurrently against the same immutable root view before RRF; text-only responses return the already ranked rows directly. Request-local timing separates vector index, reconciliation and document acquisition. Unexpected transport failures and server-side rejections retain their causes in native Effect error logs at the gateway, namespace coordinator and term-projection boundary. Expected client rejections remain ordinary responses; the public error contract stays unchanged. The R2 root references pending vector jobs, whose payloads are canonical logs. Native Cloudflare Queues schedule them, with a dedicated dead-letter queue. Upserts and deletes are submitted in batches of at most 100, and completed jobs are removed with manifest CAS. Lost acknowledgements cause safe replay with deterministic revision-specific vector ids. Acceptance is distinct from visibility. Vector ids incorporate namespace epoch, document id, and revision, so a reordered old mutation cannot replace a newer vector. Query results are reconciled with live R2 records. Configured equality, membership and numeric intervals use native metadata pre-filtering. Negative/existence predicates, unconfigured fields and stale candidates can still underfill the bounded candidate set. The local vector fixture tests transport and synchronization behavior; it cannot establish ANN recall or service guarantees.

## Resource limits

HTTP JSON bodies are bounded to 1,900,000 bytes. A write accepts at most 1,000 upserts and 1,000 deletes. Duplicate ids across a batch are rejected. Rust log decoding is bounded to 2 MiB, including decompression bombs. Index segments are capped at 10,000 documents and 16 MiB encoded bytes, with independently bounded page decode. Text queries accept at most 100 results and 64 distinct normalized terms; phrases are capped at 64 tokens. Vector/hybrid top-k is capped at 50 by native full-metadata retrieval. Filters have at most sixteen conditions, each `in` list capped at 32 scalar values. Vector dimensions are currently fixed at 768 in the owning Alchemy resource and validated at the API. Compaction reads each selected segment payload in one bounded range and decodes live document pages from that buffer, avoiding one R2 call per document. A window has at most eight segments and 8 MiB of decoded documents.

One namespace is currently coordinated by one Durable Object; that object's memory is disposable. The R2 manifest and number of segments still need scale-bound validation. Sharded manifest directories, distributed BM25 statistics, export pagination, request rate limits and per-namespace credentials are not implemented. There is one deployment-owner API credential. This must not be advertised as a hosted tenant authorization system.

## Requested delivery gate

The original goal is an OSS Cloudflare-native search system with performance comparable to Turbopuffer. Local functional checks alone cannot complete that goal. Remaining evidence includes:

1. Native Alchemy deployment, exercising the compiled Worker, real R2, volatile coordination, queues and Vectorize bindings. The local-stage Alchemy plan and native production deployment have passed. Native smoke checks exercised R2 writes, text reads, asynchronous vector visibility, and Worker/Cache API hits. Broad workload and failure validation remains required.
2. Native Vectorize metadata pre-filtering for configured equality, membership and numeric intervals has passed local contract tests. Native metadata-index deployment and a 100-vector filtered ANN smoke passed: recall@10 was 1.0 for the controlled expected neighbors, and a numeric interval returned all five expected rows. Visibility took approximately two minutes in that run; broad ANN recall and throughput still need measurement.
3. Storage/recovery tests and retained mutation-history cost at the intended namespace scale.
4. Comparable full-text and hybrid workloads with identical documents, queries, filters, concurrency, region and consistency against Turbopuffer, recording p50/p95/p99, throughput, bytes and cost.
5. Quality judgments or a public retrieval corpus, measuring ranking quality independently of latency; independent correctness checks for updates, resets, restart and partial commits.
6. OSS publication, release reproducibility, CI and dependency/license checks.

Benchmarks from the discarded local-database prototype do not describe this R2 engine. The Rust scorer has exact block pruning, positional phrase matching and live global frequencies, but comparable latency and quality still need measurement. Immutable ranges and segment compaction must be tuned using request/byte/CPU evidence, preserving exact ranking, filtering, mutation and recovery behavior.

Architectural research: [Tidepool](https://github.com/milannair/tidepool), [Zeppelin](https://github.com/zepdb/zeppelin), and [Turbopuffer architecture](https://turbopuffer.com/docs/architecture). Their storage designs are research references; no performance numbers from those projects are claimed as Kannin measurements, and no upstream implementation was copied into this repository.

## Cloudflare cache ownership

Immutable segment ranges pass through the internal `Segments` Worker entrypoint. Alchemy enables native Workers Cache for that entrypoint and disables it for the authenticated gateway. Workers Cache supplies regional tiers and request collapsing without running the entrypoint on a hit. The internal response is keyed by the immutable segment object key, byte offset, length and physical bucket and required directory-format epoch in native `ctx.props`. Cross-version Workers Cache is enabled for immutable responses; the authenticated gateway remains explicitly disabled. This preserves cache identity when Worker code changes without sharing objects between buckets. Response-format changes must use a new private entrypoint path. Cache API inside the entrypoint retains ranges in the originating data center, with bucket and format-epoch identity included in its private key. It is an additional best-effort derived layer, not canonical storage. The segment caches store neither credentials nor mutable manifests. A separate internal Cache API namespace holds point-in-time R2 manifests only for explicit edge-eventual text reads. The internal Cache API may retain a snapshot for two seconds to avoid relying on subsecond HTTP expiry, but every read enforces the stricter one-second selection limit. A valid process-memory snapshot returns without opening Cache API; any background refresh opens that cache in its detached request-owned task. Cache API is consulted only after an insufficient memory snapshot. Overlapping Cache API acquisitions share one pending native Promise per bucket, namespace and minimumSequence, including cache lookup, body consumption and frame decoding. Admission is capped at 64 pending identities; overflow uses independent acquisition. No response body or Effect fiber is shared. Completed and failed acquisitions remove their entries, and every caller still checks age and sequence after awaiting the decoded snapshot. Their observation time is recorded before fetching R2, and selection rejects ages of one second or more, future timestamps and snapshots below minimumSequence. Insufficient snapshots trigger an uncached R2 read; uncommitted sequence barriers return 409. Valid snapshots older than 250 ms trigger a detached Effect refresh registered with the request execution context through native waitUntil. A per-isolate in-flight set collapses those background refreshes. Foreground and background acquisitions additionally share one pending native Promise per bucket/namespace: the owning request consumes the R2 body, decodes and publishes the memory snapshot once, and other readers await the decoded value. Cache API publication runs through that request's native waitUntil and does not delay snapshot selection. Each reader checks its own minimumSequence and the original observation age after acquisition. Completion, absence and failure remove the pending entry; failures never extend the snapshot age. Effect fibers are not shared between requests. Strong queries continue through the coordinator and never read this cache. Expired snapshots are never used on storage failure. Missing and truncated objects use `no-store`. The public gateway has no route for raw segment bytes.

The private `Terms` entrypoint projects at most sixteen immutable segment directories per request. Each response contains ordered physical document frequencies, four-value block score bounds, optional shared length partitions, minimum title/body lengths among physically filter-eligible documents and an optional bounded eligibility projection for the selected filter fields. It contains no live statistics, tombstones, document text, credentials or query results. Terms, filters and the ordered object-key/header-length ranges are carried in native `ctx.props`; terms are canonically sorted and encoded once. The native cache key includes those props, bucket and the `catalog-v7` path. Workers Cache owns exact projected responses through the entrypoint, request path and native props, including bucket, ranges, terms and filters. A native miss acquires source overviews directly; the overview Cache API retains reusable physical sources across selectors. Query acquisition groups at most eight physical ranges per batch, with up to eight batches concurrent. Each batch refills at most four individual correlated-overview reads; canonical directory fallback stays serialized within the batch. This retains the eight-directory fallback bound and at most 32 offered individual overview acquisitions per query, with the existing shared body quotas. The smaller groups reduce permanently inadmissible batch publications without increasing cache or body-admission limits. Individual projections retain their existing 4 MiB process-cache budget; losing every cache restores canonical R2 reads. `termReads` counts catalog acquisitions and `termRequests` counts native entrypoint calls, so batching can reduce calls without hiding the acquired catalogs.

Before projecting a new term selector or filter, the entrypoint checks a separate four-MiB charged LRU of compressed segment overviews, then a private `raio-overview-batches-v6` Cache API entry containing up to sixteen compressed sources. One lookup restores a complete batch. Batches store at most three MiB of source bytes in a Schema-owned envelope containing the bucket, exact ordered physical ranges and base64 sources; larger batches bypass Cache API admission. Source identities include the physical bucket, ordered immutable segment keys and header lengths; terms and filters do not change them. Valid memory overviews are projected before cache-key hashing or Cache API acquisition.

An overview contains physical term frequencies/block bounds and groups of documents with identical serialized attributes. Its private four-element JSON sequence carries the term dictionary, eligibility groups, optional partition dictionaries and a shared summary pool. Dictionary values are either unsigned pool indices or inline summaries. The writer interns equal summaries within a conservatively charged one-MiB temporary budget, including tree entries, bound storage and sorting scratch; after admission fills, unmatched summaries serialize inline. Retained cache quotas are unchanged. The reader validates every inline and pooled summary, every index including unrequested or overwritten keys, the complete root arity and trailing-data rejection. It retains only requested term names and summary values. Indices are resolved only after the complete pool is validated; partition dictionaries use the same selector and remain null or one to 32 groups. Pool construction adds work to writes and cache reconstruction, and the temporary charge is not a whole-Worker peak-memory bound.

Each eligibility group stores the original attribute object and the component-wise minimum title/body length. Rust evaluates the actual filter against groups and combines matching minima. This preserves exact physical eligibility, including a null minimum when no group matches; empty predicates retain the original zero floor. Group tuples serialize borrowed JSON objects directly, avoiding JSON encoded inside JSON strings. Rust frames sources with decoded-length/CRC checks and validates every attribute value and group tuple. Group projection retains only fields required by up to eight distinct filter fields; larger field sets use native full-map decoding. Repeated conditions on one field retain every predicate. Discarded attribute values still pass full native JSON-value validation. Group size can grow with attribute cardinality, so decoded-page and cache admission limits remain enforced.

When both derived overview layers miss, catalog reconstruction first attempts the existing bounded compressed R2 directory acquisition and reuses its validated metadata. If that frame is unavailable, it reads headers of at most four MiB directly from canonical R2 and validates them once in Rust, including exact framing length, checksum and the existing header invariants. It projects the catalog from that retained directory without compressing an intermediate directory frame. A process semaphore admits at most eight MiB of raw headers in 64 KiB units; unavailable admission retries for at most two seconds before returning a declared unavailable response. Compressed-frame waiting does not occupy this raw-body budget. Permits remain held through canonical body settlement, validation and decoded admission. Pending readers of one source share a pending native Promise carrying completion, without sharing Effect fibers and retain their own validated directory references; failed acquisitions release the shared lifetime. Larger headers keep the existing compressed acquisition path. The ordinary ranking directory path and stored formats are unchanged.

Partial memory hits reuse their validated catalog during fallback. Missing sources project summaries/minima directly from the validated directory while building one reusable overview; it is not immediately decompressed again. Failure to build that disposable overview skips admission and still returns the validated catalog. Corrupt cached sources are discarded. An optional R2-derived overview is checked before reading the canonical directory; absence, identity mismatch, invalid encoding or unavailable cache storage falls back to the canonical source. Root tombstones/live frequencies stay query-local. Process eviction clears the LRU and can recover it through Cache API. The v5 overview namespace validates the physical source envelope; the v6 catalog route retains the projected result format. Canonical R2 root/index/log formats remain unchanged.

Rust can derive a stronger overview from an immutable segment without changing its bytes. Every term uses the same document partition, ordered by title/body length pair and coarsened to at most 32 groups. Per-group maxima of title/body frequencies and minima of lengths conservatively bound each term. Summing terms inside each group, then taking the maximum group sum preserves length correlation that independent per-term maxima discard. The effective bound is the minimum of this correlated bound and the existing independent bound, using fresh global live statistics and the same scoring order. Filters may clamp the physical length floor; tombstones only loosen the physical synopsis. Exact ranking, phrase verification and tie order remain unchanged.

Successful new segment writes and compaction attempt to store this disposable synopsis under `cache/correlated-pool-v1/` before publishing the canonical manifest. Cache failure does not fail the canonical write. Existing segments may be warmed explicitly from their canonical bytes. The concrete JSON envelope binds the physical bucket, immutable segment key and header length to a base64 Rust CRC frame. Readers cap envelope objects at two MiB, frames at one MiB and decoded frames at sixteen MiB; builders cap group/term entries at one quarter of vocabulary size, clamped to 512–65,536 entries. Singleton terms retain their ordinary physical bound in every group and add no partition entries. Expanded synopses exceeding this budget are omitted. Over-budget segments retain the ordinary path. Alchemy owns cache retirement through a thirty-day lifecycle rule, independently of canonical segment collection. No manifest, receipt, outbox or result row depends on the cache. `correlatedReads`, `correlatedHits` and `correlatedBytes` report native R2 cache acquisitions separately from logical posting range counters. A missing synopsis adds one unsuccessful cache lookup before canonical fallback; cache-loss behavior remains correct but need not retain its latency improvement.

Keys include the bucket, immutable segment key, header length, entry kind and term or filter selector. A projection retains its dictionary and shared length partitions atomically. A bounded eligibility projection retains every physical attribute group for the sorted unique filter field set, with minimum title/body lengths per group. Changing only predicate values can evaluate this model locally through the same Rust filter matcher instead of requesting another catalog. All three entry kinds share the existing four-MiB budget. Models describe physical rows only: current tombstones, global statistics and exact filter checks still apply before ranking. Eviction removes an individual selector instead of every selector for a segment. Cache updates encode only the inserted value, without copying and re-encoding the segment's accumulated selector maps; cache hits only refresh LRU order. A dictionary is never combined with partitions from another projection. Projection selectors use the sorted Bloom candidates for each physical segment. A miss group requests the union of its needed terms; a Bloom-negative term is physically absent from that segment, so the union cannot introduce a real dictionary entry outside its selector. Changing only filters reuses the projection; changing only terms can reuse eligibility. Terms excluded by every segment Bloom are removed from non-positional execution and plan identity, while phrase order stays intact and all/phrase impossibility checks still run against the complete requested term set. Query-local references survive concurrent eviction. Missing parts are acquired in separate ordered groups: full projections, dictionaries without filters, or eligibility-only projections with zero terms. Groups run sequentially inside each window, with up to eight windows concurrent; final catalogs restore input order before live statistics are aggregated. The internal zero-term projection has a current eligibility-only consumer and does not change public text-query validation. Clearing immutable memory also clears these entries, while native/Cache API projections remain disposable shared layers. Global live frequencies are still recomputed against the selected root and its removed frequencies. All segments are prioritized by descending projected score bound and then ascending UTF-16 minimum id. Tombstones and filters remain exact in the ranker before top-k. No bound-only path acquires a full directory. Candidate ranking and result materialization acquire directories only when needed.

## Vector metadata lifecycle

Alchemy provisions equality and numeric indexes for each configured field slot, up to five fields and ten native indexes. The runtime stores a SHA-256 digest of Schema-encoded scalar values in each equality slot, avoiding the provider's string truncation and preserving scalar type and null distinctions. Numeric slots retain native float64 values. Pushdown stays below the provider's 2048-byte filter limit and uses its supported bound combinations. The original R2 predicates always run after candidate reconciliation.

Every stack deploy runs the native Command.Exec metadata migration without memoization. It inventories namespace prefixes through the authenticated paginated operator API and rebuilds vectors in batches of at most 100. Rebuild checkpoints store the immutable root view and field layout in R2, and cursors are validated. Resumed pages reconcile revisions, deletion and physical compaction against the current R2 root. A namespace reset or field-layout change rejects the old cursor. Native upserts are deterministic by epoch, document and revision, so page retries preserve identity. Checkpoints remain available for retries for seven days from their R2 upload time, including completed checkpoints. Expired cursors return 410 and require a new snapshot. Vectorize indexing visibility remains eventual.

The deployed metadata migration inventoried seven existing R2 namespaces and resubmitted two existing vectors. The deployment graph references complete native index outputs before supplying the field binding, and the migration references the complete Worker output before consuming its URL. Referencing the stable URL alone allowed migration to start against the previous Worker; the ordered resource references now own that dependency.

## R2 segment collection

`collect` runs under the namespace coordinator semaphore. Each invocation reads the active root, inventories rebuild checkpoints, then visits at most 100 segments using native R2 cursors. The active root and every unexpired checkpoint pin their referenced segments. Checkpoint inventory is bounded to 1,024 objects, 8 MiB per checkpoint, 32 MiB total checkpoint input and 16,384 unique segment references; exceeding either budget fails before deleting any segment. Expired checkpoints can be removed while inventory is built.

An unreferenced segment gets a separate retirement marker with its key, ETag and observation time. Its original upload time does not start the quarantine: a segment may have been live until moments ago. A subsequent collection can delete the segment only after 24 hours with the same ETag, an observation at least as recent as the object upload, and no current pin. A newer upload restarts the quarantine even when identical bytes preserve the ETag. Replacement resets the quarantine, a future timestamp resets the observation, and a current pin cancels the marker. Deletion precedes marker removal, making interrupted deletion retries safe. Malformed markers and unavailable checkpoints fail closed. Derived retirement markers do not change the canonical root schema.

Edge text evaluation has a 30-second response deadline after snapshot selection; selection itself requires a snapshot younger than one second. The 24-hour retirement quarantine therefore covers those detached readers. Strong queries and rebuild pages serialize with collection and cannot race a physical deletion. The collector does not delete logs, receipts or old Vectorize epochs. It is an explicit operator operation; automatic scheduled collection and Vectorize epoch reclamation remain outstanding.

## Bounded independent query reads

Text evaluation loads candidate segment dictionaries with at most eight concurrent batch reads, then computes global live document frequencies in manifest order. An isolated native cold-summary comparison found no latency benefit from reducing that limit to four; two and one were slower. The measured decision is recorded in [performance](performance.md#native-cold-catalog-concurrency). Within each batch, immutable catalog memory hits are retained and touched independently; only missing ranges enter the internal Terms request. Returned catalogs are merged by original batch position before live frequency aggregation, including when cache admission evicts another query-local hit. Exact segment score bounds are evaluated in batches of at most 64 catalogs, decoding the shared namespace statistics once and constructing each encountered term's BM25 scorer once per batch. The temporary scorer map borrows catalog keys and is dropped with the batch; block maxima and eligible field-length minima remain segment-specific. The returned bound count and finite values are checked before priority sorting. Only competitive segments acquire the full posting directory from the Rust directory already loaded for ranking. Offsets, first/last rows and block counts are absent from the cached score projection. Score projections retain only unique field-frequency maxima and field-length minima tuples per term. Their order and multiplicity have no scoring meaning: segment bounds take the maximum over those tuples. Document frequencies, eligible filter minima and the canonical posting/block directory remain unchanged. Derived catalog cache versions change with this projection; no R2 migration is required. Within each scored segment, requested term spans are grouped in their original order. Coalescing admits at most 16 KiB of additional gaps per group and a combined range of at most 1 MiB; larger individual spans retain their existing segment bound. Up to four grouped ranges are acquired concurrently. The reader validates ordering, gap/size budgets, positive lengths and segment bounds, then passes only the selected subarray slices to Rust in the original block order, preserving the strictly increasing row invariant. Gap bytes are transferred and charged but never decoded as postings. Final hit documents also load with concurrency four and preserve ranking order. Within each Rust segment ranker, exact block bounds are prepared lazily when top-k first fills and reused for subsequent pruning. Block selection remains the original linear first-match lookup and bounds are summed in sorted term order; the cache belongs only to that finish operation. Any-mode candidates begin with union traversal. Once top-k fills, the cursor computes each term's maximum conservative block score and selects the largest upper bound, preferring the shorter posting list on a tie. If the cutoff strictly exceeds the sum of every other term's upper bound plus the existing tolerance, every competitive remaining document must contain that term. The cursor then uses its posting list as a driver and seeks the other lists to each candidate before scoring. The cutoff never decreases, so the requirement remains valid for the rest of that finish operation. Sorted-term score accumulation, equal-score ID ordering and posting validation remain unchanged. All/phrase candidates use the shortest posting list as a driver, skip excluded driver rows before alignment and seek other lists with adaptive exponential/binary search. A terminated list ends the intersection. When every list covers every physical document, row positions coincide with their indices; cursors synchronize only after excluded rows cause divergence. Valid candidates retain the original sorted-term score accumulation and repeated-token phrase order. Each planned segment carries an upper match count from live physical document frequencies: any uses their sum capped by live documents, and all/phrase use their minimum. Attribute filters can only reduce those counts; no eligible attribute group gives zero. Invalid live cardinalities fail rather than being clamped; DF lookups use own record entries through native Maps, including ordinary terms such as `constructor`. Initial candidates may run together when their combined ceiling cannot exceed the missing top-k slots, because no still-possible hit can be pruned by an earlier cutoff. Otherwise the first prioritized segment runs alone. Later windows retain the original four-position boundaries and admit at most four segments. An incomplete top-k caps its next window by the number of missing result slots when the previous window returned matches; a window without matches retains parallel exploration. A complete top-k retains sequential evaluation through the first four candidate positions for early pruning. A four-permit limit is shared across directory and posting acquisitions. Each window uses the cutoff from the preceding completed window; its results merge in stable score/ID order before the next window. At most four grouped ranges per segment are acquired together. Four retained rankers and four in-flight reads are per-query limits, not a total Worker memory bound. No query-result caching is introduced. Cold concurrent workerd requests are checked against the strong scorer for identical IDs, revisions and scores.

Query responses expose request-scoped Server-Timing for dictionary acquisition, ranking/posting acquisition and result-document acquisition. Edge responses additionally measure snapshot selection; coordinator and gateway totals are retained. These are elapsed intervals, including I/O, rather than CPU measurements. `tooling/load.ts` records each response's timings alongside its latency samples without deriving per-request statistics from shared counters.

The benchmark bucket's recorded physical location is `enam`. Cloudflare currently lists R2 hints for western/eastern North America, western/eastern Europe, Asia-Pacific and Oceania, and does not list a South America hint. Hints apply at creation and are best effort; a bucket's existing location cannot be relocated by updating its hint. A location hint therefore cannot remove the coordinator hop by placing this existing object in Brazil; this constraint is separate from gateway and R2 placement. See [Durable Object data location](https://developers.cloudflare.com/durable-objects/reference/data-location/).

Warm edge namespaces retain decoded snapshots in an isolate-owned LRU before using Cache API. Entries keep their original R2 observation timestamp; neither a memory hit nor Cache API rehydration extends freshness. The cache is capped at 24 MiB of conservative charge, using four times the encoded UTF-8 size per snapshot; oversized snapshots bypass this layer. Namespace and bucket identity stay in the key. Invalid ages and insufficient sequence barriers trigger fresh R2 acquisition. The LRU may retain an expired snapshot with its R2-sourced ETag as a conditional-read candidate; it is never eligible for ranking solely because it remains in memory. A native conditional get confirms an unchanged ETag without a body, then establishes a new observation timestamp measured before that read. Changed content is fetched and fully decoded. Native [timingSafeEqual](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/#timingsafeequal) compares the equal-length views, including their offsets. Cache response headers never supply origin provenance. A missing origin or different payload still requires a full R2 read on the next refresh. Rehydration keeps the cached frame's own observation timestamp; preserving an ETag never extends that lease. The same age and sequence checks apply after either acquisition path. `edge_snapshot_revalidated` marks foreground conditional-read confirmation, and health counters report body bytes and confirmations. Strong reads never use either snapshot cache. Cache API remains the shared data-center layer. Snapshot responses carry the original observation time and manifest sequence in validated headers, so missing metadata, expired/future ages and insufficient sequences discard the body before JSON decoding. An eligible body still undergoes full Schema validation and the original age/sequence checks. Headers never extend freshness or authorize a stale body. Per-request `edge_snapshot_cache_rejected` marks this early rejection; health counters expose snapshot decodes and header rejections. Immutable segment ranges retain the native Workers Cache regional tiers.

Vector synchronization still processes version-specific deletions, but only submits upserts whose epoch and revision remain live in the canonical R2 root. Superseded jobs are acknowledged without allocating obsolete provider vectors. The indexed-field configuration is decoded once per synchronization operation. This removes unnecessary mutation and storage work; it does not reclaim vectors that an older provider mutation already made visible before the revision changed.

## Bounded Queue batching

Vector consumers receive up to sixteen messages per batch, index consumers up to eight, with a one-second batching window and at most four native consumer invocations. The Worker processes at most four messages concurrently. Namespace Durable Object semaphores retain serialization of canonical mutations. These are separate concurrency limits, not a claim of sixteen-fold throughput.

A validated vector notification drains up to sixteen canonical jobs, rather than only its own sequence. Only a notification still referenced by the canonical root may trigger that drain; duplicate or retired notifications submit zero jobs. Log identity and namespace are checked before dispatch. Upserts and version-specific deletions share bounded buffers across the selected jobs, flushing at 100 entries and committing the root only after all provider submissions succeed. Live revision/epoch checks prevent superseded jobs from allocating provider vectors. Provider failures retain the outbox and replay deterministic identities.

Every queue message owns its acknowledgement or retry, including decode failures and failed binding calls. A malformed message retries without cancelling a healthy sibling. Response bodies are consumed before acknowledging. Dedicated dead-letter queues remain provisioned.

## Query encoding and cache decisions

The original term order, the sorted projection selector, filters and global statistics are each encoded once per text query for their repeated consumers. Each ranker still receives its own tombstones. The candidate array is already sorted after each segment merge, so no duplicate final sort is performed. Exact score bounds, returned rows, snapshot age and authorization remain unchanged.

A twelve-query cold local regression observed thirteen immutable range reads, the same as one query in that fixture; ten isolated repeats also passed after switching to physical bucket identity. That full-query evidence alone did not justify another acquisition owner. A later direct range-boundary test demonstrated duplicate body consumption despite native collapsing; pending-only sharing now addresses that separate cost, as documented above. Native deployment still has cold directory-acquisition tails; local cache efficiency does not establish regional latency guarantees.

Workers KV was evaluated for mutable snapshots and immutable derived data. Its documented propagation and negative-cache delays can exceed sixty seconds, incompatible with this engine's less-than-one-second snapshot contract. Immutable bytes already have native Worker Cache tiers and local Cache API ownership; another KV copy would introduce a read/write path without demonstrated benefit here. R2 remains canonical, with no new stateful dependency. See [KV consistency and caching](https://developers.cloudflare.com/kv/concepts/how-kv-works/) and [Queue batching and retries](https://developers.cloudflare.com/queues/configuration/batching-retries/).

These counts include memory/shared acquisition reuse and do not equal R2 origin calls or transfer. Native clocks can remain unchanged during uninterrupted CPU work; zero durations are not CPU measurements.

Query Schema decoders, encoders and namespace/operation guards are created once per isolate. Effect retains the compiled parser on each native adapter; constructing a new JSON Schema and adapter for every segment discards that identity. Request data, validation options and results remain query-local. Two alternating local comparisons over 50,000 documents and 100, 30 and 8 segments checked 2,688 identical responses, including exact scores and sequence barriers. Rare-query medians improved by 8–28%; common-query medians improved by 2–18%. The native production CPU profiler can identify work that elapsed request timers miss. Queries with more than four candidate segments may retain conservative ranking bounds in a one-MiB process LRU. Each bound pairs an upper score with the smallest possible ID at that score, using the same UTF-16 order as the Rust scorer. The upper score covers both returned hits and the external cutoff used to omit pages. With no external cutoff, the physical source minimum starts the certificate. The ID bound applies only at the upper score: lower-scoring rows can have earlier IDs. Cache updates retain the tighter certificate, preferring a lower upper score or a larger minimum ID at equal score. Planning combines it with the catalog bound, prioritizes the same score/ID order and preserves the existing numeric pruning tolerance. Requested top-k does not change certificate validity. Current canonical manifest acquisition, authorization and minimumSequence checks remain authoritative; no result rows or root authority enter this cache. Charging includes the key, retained ID and entry overhead, with LRU eviction and namespace rebuild invalidation. Health/metadata expose retained charge and entry count, not whole-Worker peak memory.

The original request text still reaches the Rust ranker. The physical bucket and namespace/object prefix scope the cache key. Current manifest acquisition, authorization and minimumSequence checks precede planning. On a hit, current segment objects receive the retained eligibility/bounds; learned score bounds remain separately scoped to exact scoring inputs. Top-k does not change plan validity. Missing, evicted or oversized plans use the original catalog path. Entry charge includes four times encoded plan length and key length plus entry overhead; namespace rebuild clears the plan entries. This reallocates one MiB from encoded directories while preserving the fifty-two-MiB cache quota sum and does not establish total Worker peak memory. Metadata/health report plan charge, entries and process-local hits.

The version binding is provisioned by Alchemy; no manual engine-version setting or cross-deploy scoring reuse is used. After ranking, each segment's original catalog certificate can be tightened with a learned score/ID certificate; omitted pages remain covered by the external cutoff. Unranked segments retain their original safe bound. Memory retains the tightened plan immediately. A new or improved plan is offered as a compressed Rust CRC frame with a one-hour cache lifetime through the owning HTTP or Durable Object context’s native `waitUntil`. Publication does not delay row materialization or query completion. Canonical R2 segments and manifests are unchanged.

Shared-frame admission caps encoded JSON at one MiB and compressed bytes at 256 KiB. Concrete Schema-encoded headers declare both lengths. Read admission charges the larger of compressed size and four times declared inflated size in 64-KiB units against a four-MiB target. Readers require exact agreement between headers, actual compressed bytes and the native frame length before unpacking, verify Rust framing/checksum/decompression limits and the concrete SharedTextPlan Schema, then require matching selection identity, Worker version, segment count and current document/title/body totals. Tests simulate the same deployed version across fresh workerd instances with a stable native-shaped version fixture; production uses Cloudflare's actual binding. Text-plan, ANN-candidate and immutable overview-batch publications share one process-owned admission owner in storage. Overview batches carry their bucket, ordered immutable key/header-length references and complete overview bytes. The v6 Cache API representation is JSON; the same envelope is packed into a CRC-checked Rust frame for the R2 backstop. Batches of eight or more sources use namespace-scoped `cache/correlated-pool-batches-v1/<first-source-key>/<ordered-range-digest>` objects, covered by the existing correlated-cache lifecycle. After memory and Cache API misses, R2 batch lookup has a nominal one-second shared outcome and at most sixteen pending sources. Size, declared length, frame length/CRC, bucket, ordered references and overview count must agree. A hit repopulates memory and schedules Cache API promotion; misses, unavailable admission and invalid frames recover through individual correlated summaries and canonical directories. Preparation covers that complete resident tail window, with a 384-KiB combined-input guard and the existing 512-KiB encoded/frame limits. Other selections and unavailable entries retain query-driven preparation. Cache publication can precede demand and shares the existing admission budget. Catalog responses do not await optional Cache API storage. Overview publication telemetry measures foreground encoding and admission, not background storage completion. ## Catalog acquisition

Decoded frequency pages memoize successful document-row and token-position validation against the exact retained Rust directory header. A weak reference preserves allocation identity without retaining header contents after the last directory or ranker releases them. A different parsed header always validates again, and failed validation never enters the memo. Single-row pages keep the original validation path. Every attachment still enforces requested terms, any/all mode, cross-page row ordering, current filters and tombstones; phrase queries retain positional validation. The existing shared cache budget conservatively charges the weak-reference control allocation. Canonical bytes and ranking statistics are unchanged.

Private term responses carry Schema-validated origin telemetry. Public request timings distinguish native Worker hits, Cache API hits and newly executed origins; cached responses never replay stored origin intervals as current work. When every requested immutable overview is resident, Terms skips its optional selector Cache API lookup and lets the existing projection reader validate the retained bytes. A presence check never authorizes a result: eviction or invalid bytes still take the reader through overview-cache and canonical fallbacks. Otherwise the selector lookup and publication retain their existing behavior. Detached readers retain their attempt and body permits through any nonabortable body and validation after a foreground timeout. Writers and compaction prepare eligible directory frames alongside correlated summaries after the canonical segment write.
