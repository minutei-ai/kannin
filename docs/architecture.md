# Architecture and completion gates

Kannin is a separate OSS repository. No Minutei production data, fixtures, secrets, or services are bundled.

## Ownership

The Worker authenticates every namespace operation. Writes and default strong reads route to one volatile Durable Object coordinator. Explicit edge-eventual text reads select a bounded-age R2 snapshot and run the same Rust scorer in the edge Worker. If acquisition returns a snapshot outside that age budget or below the requested sequence, the original authenticated request routes to the coordinator, which validates the sequence against its current view. Expired snapshots never participate in ranking. This recovery can add the coordinator's network hop; its response carries request-local `edge_snapshot_fallback` timing. Canonical decoding/storage failures still fail, and an uncommitted future sequence still returns 409. Each object serializes mutations and strong-read manifest capture with an instance-owned Effect semaphore. Up to four strong queries run outside that semaphore after capturing an immutable root; queued readers capture only after admission. A read therefore observes its captured sequence even when a later reset or compaction commits. In-flight reader leases pin their segments during collection and release on success or failure. Collection rejects more than 16,384 unique references before deleting segments. Query failures do not clear concurrent writer state. Response timings separate admission/coordinator wait (`query_wait`) from canonical root acquisition (`query_root`); neither establishes CPU use or network placement. Concurrent namespaces remain independent. The application never calls `ctx.storage` and never opens a local database. The coordinator caches the R2 manifest; all searchable data and recovery state belong to R2. Rust/WASM owns immutable index construction, positional postings, field-normalized BM25, exact block-bound pruning, filters, log compression, integrity checks and the shared text normalization used for both indexing and queries.

The internal snapshot Cache API namespace uses a versioned binary frame: eight magic bytes, a little-endian metadata length, a Schema-encoded observation timestamp/sequence and retained manifest JSON bytes. Canonical R2 stays at its existing format. A fresh R2 body is decoded and validated once, retaining its original UTF-8 bytes for the frame instead of reserializing the complete manifest. An unchanged conditional R2 ETag reuses both the decoded manifest and retained payload. A retained per-entry timestamp groups Cache API publication attempts within 500 ms only for unchanged ETags; changed bodies publish immediately. Suppressed publications neither build a full payload Blob nor rewrite an older cached frame's observation time. Memory snapshots still use their own new canonical observation; every reader enforces the same one-second age and sequence barrier. Cache eviction or unsuccessful publication can leave other isolates with a miss until the next attempt; those readers recover through R2. Health reports isolate-local publication attempts, offered frame bytes and skipped publications, not storage receipts or billed usage. Cache readers validate framing, metadata, canonical Root Schema, matching sequences and body age; HTTP metadata only rejects ineligible bodies before decoding. Corruption recovers through R2. The cache cutover uses one new namespace without a legacy reader. The 24 MiB process LRU charges four times the larger of frame size and retained backing-buffer size, including payload views into a complete frame. Health reports charged bytes and retained payload buffers separately; these counters do not establish total Worker peak memory.

R2 owns canonical mutation logs, receipts, index segments and the atomic root. A write's sequence is assigned by the namespace coordinator. The segment and log are prepared before I/O and stored concurrently under separate immutable object keys. Both writes must complete successfully before a conditional root update. The root, rather than object listing, defines which documents committed. Receipt acknowledgement and queue submission follow that commit. Receipts use a conditional create; a collision reads and validates the existing receipt. The coordinator remembers only its last confirmed receipt to avoid repairing that same acknowledgement before every warm write. Losing this memory restores the canonical R2 repair path. A request may fail after committing in R2; retry the same request id and payload. The manifest retains the last receipt so an interrupted receipt write can be repaired before another mutation. Logs and idempotency receipts are retained indefinitely. Collection never deletes them, so request-id reuse keeps its original conflict/idempotency behavior; operators must budget this retained history.

Header parsing validates UTF-8 once before the native JSON string reader; framing, CRC and structural checks remain required. Internal directory acquisition uses a separate immutable `/directory-v1` cache resource. Rust compresses the complete canonical header into a versioned frame carrying its exact decoded length and CRC. Decoding checks the manifest-declared header length, caps inflation at 16 MiB, verifies the outer checksum, then applies the unchanged canonical header parser and checksum. R2 segment bytes and posting/document offsets are unchanged. Encoded directories have an eighteen-MiB pool: seventeen MiB for charged frames and one MiB for bounded access counters. One MiB holds learned segment score bounds and another MiB holds compact text plans. Decoded-directory admission is twenty MiB, and raw ranges/frequency pages retain twelve MiB, keeping these cache quotas at fifty-two MiB total. The forty-MiB individual decoded-directory validation limit remains; larger-than-admission directories remain scoped and uncached. Admission only displaces a resident frame when the incoming access count exceeds every required victim count. Counts saturate at 255 and halve every 4,096 encoded-directory lookups; cold counter entries disappear, and namespace invalidation clears both frames and history. Raw buffer charges include keys/entry overhead, while payload bytes remain separately reported. These are cache quotas, not a bound on active rankers, transient decoding or complete Worker peak memory. Cache identities keep the bucket/object prefix used by namespace invalidation, with a format suffix separating compressed directories from raw ranges. Document-range batching still tests raw-range identities, and in-flight acquisition sharing remains format-specific. Cache API and Worker Cache retain this derived representation without query-selector keys. Each immutable segment has a versioned, CRC-checked header and independently compressed, length-bounded, CRC-checked document/posting pages. Postings encode local row ids, title/body term frequencies and token positions with delta varints. Any/all scoring stores compact row/title-frequency/body-frequency lists; phrase scoring retains positional lists. Both readers validate every varint, including position ordering/overflow, CRC, decoded length and document-position bounds. After validating every decoded posting, the scorer retains only rows allowed by filters and tombstones. A separate per-term last-decoded-row map preserves block-order validation even when excluded rows are discarded. New filter masks retain only attributes named by their filters; small-field overview projections use the same reader. Unused JSON values are traversed without constructing value trees, while preserving number, string, nested structure and recursion validation. Cached masks remain keyed by the complete filter and tombstones remain query-local. Full term catalogs still supply global statistics and conservative score bounds. The shared scoring/cursor algorithm is monomorphized for each list representation, with no per-row dynamic dispatch. A lazy, request-local Rust PreparedQuery parses shared ranking input, normalizes words, sorts and deduplicates term indices, compiles BM25 scorers and records repeated-token phrase order once. Segment rankers share that immutable preparation; each selected segment still applies its own filters and tombstones. Its constructor requires an empty shared dead-row list, and the segment ranker receives the actual list separately. Native DisposableStack lifetime releases the plan on completion/error, while rankers retain the reference-counted immutable term preparation and remain valid after plan release. The plan retains normalized words, statistics, sorted indices, scorers, phrase order, mode, top-k and filters; original query text and the empty shared tombstone vector are released after validation. Segment eligibility and posting lists remain independently owned. No compiled query enters a process cache. Top-k scoring reserves its bounded heap once and replaces the worst hit only when a candidate wins the existing score/row comparison. Noncompetitive candidates do not enter the heap; the heap never needs a transient k-plus-one hit. Search list storage is internal; Rust callers use `Search::add` and `Search::finish` rather than the former public `lists` field. The persisted posting layout and HTTP contract are unchanged. A block directory stores ranges and conservative frequency/length bounds. R2 range reads fetch only needed posting pages and result documents. Rust projects only selected document byte ranges for result acquisition, avoiding a second serialization of document attributes. Up to four consecutive physical rows from the same immutable segment may share a read of at most 1 MiB, without gaps or overfetch. Page references are sorted only to select that range; decoding and returned rows preserve the original ranking order. Text, vector and hybrid materialization use this acquisition policy, with sparse rows and mixed segments retaining individual reads. A query-local semaphore bounds directory, document and related I/O to four operations. Text ranking evaluates the first four prioritized segments sequentially, then processes at most four eligible segments per window against the cutoff established before that window. Header acquisition and posting ranges share four permits; decoded rankers are released at the window boundary. Each window merges its bounded top-k before selecting the next. An older cutoff can cause extra reads but cannot exclude a winning row. Preparation/acquisition timing counters sum segment intervals and may exceed the overlapping ranking wall time. Before posting acquisition, the Rust ranker omits blocks whose complete row interval is excluded by filters or tombstones. Once earlier segments supply a full global top-k, it also omits pages whose conservative complete-query score bound cannot beat that cutoff. The bound sums each term's maximum block score across overlapping row intervals, using live global statistics and sorted-term addition. Equality pruning compares the first eligible document identifier in UTF-16 order; the existing strict-score tolerance remains unchanged. Competitive rows retain all contributing term pages. The original span builder regroups retained pages within the same gap/length budgets; the first segment still has no global cutoff. Without one, any/all may derive a local lower cutoff from terms present in every physical document. It evaluates a minimum one-occurrence score across legal nonempty fields for currently eligible rows, retaining a bounded top-k heap. Page upper bounds use the minimum title/body lengths among currently eligible rows in each term block, clamped against that block's original physical minima. A block with no eligible row contributes zero; unrestricted masks use the original physical bounds. The same query-local bounds serve acquisition and finish-time pruning, with no persistent mask-derived metadata. Any needs at least one such term, all needs every requested term, and phrase keeps the original path. This cutoff includes its own kth identifier because its supporting rows have not yet entered the final ranking; insufficient positive eligible rows use the original spans. Remaining blocks share a span when each excluded byte gap is at most 4 KiB; larger gaps split the span. Only selected pages are decoded, and each retains CRC and token-position validation. Spans remain bounded to the segment size and reads run in windows of four. Global document frequencies and score bounds still use the complete immutable term catalog. Every document page retains its own CRC and Schema validation; copied page buffers are separately charged to the existing range LRU so subset queries can hit memory without retaining an uncharged larger backing buffer. The native shared cache retains merged ranges. A different subrange after memory eviction may miss those entries and fall back to R2. Concurrent readers of the same bucket/object/offset/length additionally share one pending native acquisition per isolate. Its owner consumes the response body and validates its length before resolving immutable bytes; responses, readers and Effect fibers are never shared. Success and failure remove the entry. The pending map tracks at most 64 acquisitions and bypasses tracking at capacity. A shared process-owned LRU retains immutable range bytes and decoded Rust frequency pages within the same 12 MiB budget. Any/all pages with repeated title/body occurrences may retain checked rows, counts and final positions; phrase and single-occurrence pages use the original decoder. Cache admission validates compression, CRC, lengths, every varint and position ordering once. Every ranker attachment still checks document/position bounds, block order, filters and current tombstones. Physical bucket/object/offset/length identifies each immutable page; eviction and namespace clearing release its WASM handle. Metadata and health expose raw rangeCacheBytes and conservatively charged postingCacheBytes separately. Compressed range acquisition still occurs before attachment; this cache avoids repeated decoding rather than origin reads. Decoded Rust directories have a separate 20 MiB conservatively charged admission budget and a 40 MiB individual validation ceiling and deterministic reference-counted leases; retained Rust Bloom batches have a 4 MiB charged budget including bitsets, offsets, cache keys and prefix metadata. Query-selected immutable term catalogs have a separate 4 MiB conservatively charged LRU. All storage caches use the physical bucket name and immutable object version, so distinct native binding references to the same bucket share entries. Each directory includes a conservatively charged 32 KiB filter-mask budget, capped at 16 entries; masks derive solely from immutable attributes, and tombstones apply on a query-local copy. Filter-aware segment score bounds use minimum eligible field lengths without weakening exact ranking. Rust retains a query-local block-bound cursor per term after top-k fills; postings advance monotonically, so a binary search is needed only when the current bound no longer covers the posting row. Segment parsing rejects reordered or overlapping posting block row intervals. Score arithmetic, pruning tolerance and tie order remain unchanged. These caches are disposable. Blooms in the root prune unrelated segment reads. Probe inputs and hashes are shared across batches of at most 64 bitsets, with bounded packed buffers and checked offset framing. Immutable batches retain their bytes inside WASM so cache hits avoid JavaScript repacking and host-to-WASM byte transfer. Identity includes physical bucket, Bloom field and ordered immutable segment keys, preserving reuse after manifest rehydration. Eviction and namespace rebuild free native handles; oversized batches bypass retention with scoped release. Document reconciliation visits aligned sixty-four-segment windows newest first, including a partial newest window, then reverses matches within each window. It removes IDs already resolved and retains exact lookup/tombstone checks. For `all` and phrase queries, a negative Bloom intersection across every segment returns empty before acquiring directories. When an intersection remains possible, all candidate dictionaries still contribute global document frequencies; segments missing a required live term are then skipped before posting reads. Bloom false positives can add work but cannot remove valid matches. Tombstoned rows and per-segment removed document frequencies keep namespace-wide scoring correct across updates and deletions.

Recovery loads the root and its referenced index objects; it does not replay a database or require the log to construct a hot index. Losing all coordinator memory therefore preserves committed state. Native Cloudflare Queues schedule bounded compaction; explicit compaction also builds a new immutable segment from live records and activates it with root CAS. Original document revisions, attributes, vectors and global statistics survive physical moves. The explicit paginated collector quarantines superseded and orphan segments before physical deletion. CRC32 detects accidental corruption; bucket authorization, rather than CRC32, controls who may modify canonical objects.

Vectorize owns the ANN index. Native Cache API retains successful nonempty candidate lists for at most one second of HTTP freshness. Its internal key includes the physical bucket, namespace epoch, canonical sequence, pending vector jobs, vector, filters and indexed-field configuration. Writes, resets and outbox transitions therefore select different keys. Cache misses, expiry, invalid cached data and cache unavailability use the native provider; empty lists and failures are never stored. Provider visibility remains eventual and a cached list can add up to one second before an asynchronous index change is observed. Every cache hit still acquires the current strong R2 view through the coordinator and reconciles candidates before materialization; document or query-result authority is never cached. Request-local `vector_cache` timing labels distinguish hit and miss, and `vector_index` now includes cache selection and acquisition. Query candidates are reconciled with the current R2 root in ordered windows before document materialization. Each window covers the remaining requested count, with a minimum of four candidates; processing stops once enough live eligible candidates are found or the provider list ends. All provider metadata is decoded at its boundary, and skipped stale/residual-filter candidates allow later windows to run. Revision-specific ids, vector presence and residual filters are checked with concurrency four; only the first requested top-k eligible candidates load document pages, also with concurrency four and provider order preserved. Filters are encoded once. Empty canonical namespaces avoid provider calls after input validation. Hybrid lexical and vector reads start concurrently against the same immutable root view before RRF; text-only responses return the already ranked rows directly. Request-local timing separates vector index, reconciliation and document acquisition. Unexpected transport failures and server-side rejections retain their causes in native Effect error logs at the gateway, namespace coordinator and term-projection boundary. Expected client rejections remain ordinary responses; the public error contract stays unchanged. The R2 root references pending vector jobs, whose payloads are canonical logs. Native Cloudflare Queues schedule them, with a dedicated dead-letter queue. Upserts and deletes are submitted in batches of at most 100, and completed jobs are removed with manifest CAS. Lost acknowledgements cause safe replay with deterministic revision-specific vector ids. Acceptance is distinct from visibility. Vector ids incorporate namespace epoch, document id, and revision, so a reordered old mutation cannot replace a newer vector. Query results are reconciled with live R2 records. Configured equality, membership and numeric intervals use native metadata pre-filtering. Negative/existence predicates, unconfigured fields and stale candidates can still underfill the bounded candidate set. The local vector fixture tests transport and synchronization behavior; it cannot establish ANN recall or service guarantees.

## Resource limits

HTTP JSON bodies are bounded to 1,900,000 bytes. A write accepts at most 1,000 upserts and 1,000 deletes. Duplicate ids across a batch are rejected. Rust log decoding is bounded to 2 MiB, including decompression bombs. Index segments are capped at 10,000 documents and 16 MiB encoded bytes, with independently bounded page decode. Text queries accept at most 100 results and 64 distinct normalized terms; phrases are capped at 64 tokens. Vector/hybrid top-k is capped at 50 by native full-metadata retrieval. Filters have at most sixteen conditions, each `in` list capped at 32 scalar values. Vector dimensions are currently fixed at 768 in the owning Alchemy resource and validated at the API. Compaction reads each selected segment payload in one bounded range and decodes live document pages from that buffer, avoiding one R2 call per document. A window has at most eight segments and 8 MiB of decoded documents.

One namespace is currently coordinated by one Durable Object; that object's memory is disposable. The R2 manifest and number of segments still need scale-bound validation. Sharded manifest directories, distributed BM25 statistics, export pagination, request rate limits and per-namespace credentials are not implemented. There is one deployment-owner API credential. This must not be advertised as a hosted tenant authorization system.

## Requested delivery gate

The original goal is an OSS Cloudflare-native search system with performance comparable to Turbopuffer. Local functional checks alone cannot complete that goal. Remaining evidence includes:

1. Native Alchemy deployment, exercising the compiled Worker, real R2, volatile coordination, queues and Vectorize bindings. The local-stage Alchemy plan and native production deployment have passed. Native smoke checks exercised R2 writes, text reads, asynchronous vector visibility, and Worker/Cache API hits. Broad workload and failure validation remains required.
2. Native Vectorize metadata pre-filtering for configured equality, membership and numeric intervals has passed local contract tests. Native metadata-index deployment and a 100-vector filtered ANN smoke passed: recall@10 was 1.0 for the controlled expected neighbors, and a numeric interval returned all five expected rows. Visibility took approximately two minutes in that run; broad ANN recall and throughput still need measurement.
3. Storage/recovery tests and retained mutation-history cost at the intended namespace scale.
4. Comparable full-text and hybrid workloads with identical documents, queries, filters, concurrency, region and consistency against Turbopuffer, recording p50/p95/p99, throughput, bytes and cost.
5. Quality judgments or a public retrieval corpus, measuring ranking quality independently of latency; independent correctness checks for updates, resets, restart and partial commits.
6. OSS publication, release reproducibility, CI and dependency/license checks.

Benchmarks from the discarded local-database prototype do not describe this R2 engine. The Rust scorer has exact block pruning, positional phrase matching and live global frequencies, but comparable latency and quality still need measurement. Immutable ranges and segment compaction must be tuned using request/byte/CPU evidence, preserving exact ranking, filtering, mutation and recovery behavior.

Architectural research: [Tidepool](https://github.com/milannair/tidepool), [Zeppelin](https://github.com/zepdb/zeppelin), and [Turbopuffer architecture](https://turbopuffer.com/docs/architecture). Their storage designs are research references; no performance numbers from those projects are claimed as Kannin measurements, and no upstream implementation was copied into this repository.

## Cloudflare cache ownership

Immutable segment ranges pass through the internal `Segments` Worker entrypoint. Alchemy enables native Workers Cache for that entrypoint and disables it for the authenticated gateway. Workers Cache supplies regional tiers and request collapsing without running the entrypoint on a hit. The internal response is keyed by the immutable segment object key, byte offset, length and physical bucket in native `ctx.props`. Cross-version Workers Cache is enabled for immutable responses; the authenticated gateway remains explicitly disabled. This preserves cache identity when Worker code changes without sharing objects between buckets. Response-format changes must use a new private entrypoint path. Cache API inside the entrypoint retains ranges in the originating data center, with bucket identity included in its private key. It is an additional best-effort derived layer, not canonical storage. The segment caches store neither credentials nor mutable manifests. A separate internal Cache API namespace holds point-in-time R2 manifests only for explicit edge-eventual text reads. The internal Cache API may retain a snapshot for two seconds to avoid relying on subsecond HTTP expiry, but every read enforces the stricter one-second selection limit. A valid process-memory snapshot returns without opening Cache API; any background refresh opens that cache in its detached request-owned task. Cache API is consulted only after an insufficient memory snapshot. Overlapping Cache API acquisitions share one pending native Promise per bucket, namespace and minimumSequence, including cache lookup, body consumption and frame decoding. Admission is capped at 64 pending identities; overflow uses independent acquisition. No response body or Effect fiber is shared. Completed and failed acquisitions remove their entries, and every caller still checks age and sequence after awaiting the decoded snapshot. Their observation time is recorded before fetching R2, and selection rejects ages of one second or more, future timestamps and snapshots below minimumSequence. Insufficient snapshots trigger an uncached R2 read; uncommitted sequence barriers return 409. Valid snapshots older than 250 ms trigger a detached Effect refresh registered with the request execution context through native waitUntil. A per-isolate in-flight set collapses those background refreshes. Foreground and background acquisitions additionally share one pending native Promise per bucket/namespace: the owning request consumes the R2 body, decodes and publishes the memory snapshot once, and other readers await the decoded value. Cache API publication runs through that request's native waitUntil and does not delay snapshot selection. Each reader checks its own minimumSequence and the original observation age after acquisition. Completion, absence and failure remove the pending entry; failures never extend the snapshot age. Effect fibers are not shared between requests. Strong queries continue through the coordinator and never read this cache. Expired snapshots are never used on storage failure. Missing and truncated objects use `no-store`. The public gateway has no route for raw segment bytes.

The private `Terms` entrypoint projects at most sixteen immutable segment directories per request. Each response contains ordered physical document frequencies, four-value block score bounds and minimum title/body lengths among physically filter-eligible documents. It contains no live statistics, tombstones, document text, credentials or query results. Terms, filters and the ordered object-key/header-length ranges are carried in native `ctx.props`; terms are canonically sorted and encoded once. The native cache key includes those props, bucket and the `catalog-v4` path. Cache API uses a separate versioned namespace with SHA-256 identities for ranges and the term/filter selector. Each query acquires up to eight batches concurrently, and each entrypoint request reads its directories sequentially. This preserves the eight-directory acquisition bound per query without sharing request-owned work. Individual projections retain their existing 4 MiB process-cache budget; losing every cache restores canonical R2 reads. `termReads` counts catalog acquisitions and `termRequests` counts native entrypoint calls, so batching can reduce calls without hiding the acquired catalogs.

Before projecting a new term selector or filter, the entrypoint checks a separate four-MiB charged LRU of compressed segment overviews, then a private `raio-overview-batches-v2` Cache API entry containing up to sixteen compressed sources. One lookup restores a complete batch. Batches store at most three MiB of source bytes as a Schema-owned base64 array; larger batches bypass Cache API admission. Source identities include the physical bucket, ordered immutable segment keys and header lengths; terms and filters do not change them. Valid memory overviews are projected before cache-key hashing or Cache API acquisition.

An overview contains physical term frequencies/block bounds and groups of documents with identical serialized attributes. Each group stores the original attribute object and the component-wise minimum title/body length. Rust evaluates the actual filter against groups and combines matching minima. This preserves exact physical eligibility, including a null minimum when no group matches; empty predicates retain the original zero floor. Group tuples serialize borrowed JSON objects directly, avoiding JSON encoded inside JSON strings. Dictionaries and bounds also serialize borrowed directory entries. Rust frames sources with decoded-length/CRC checks, validates every term summary, attribute value and group tuple, and retains only requested dictionary entries. Group projection retains only fields required by up to eight distinct filter fields; larger field sets use native full-map decoding. Repeated conditions on one field retain every predicate. Discarded attribute values still pass full native JSON-value validation. Missing/duplicate root fields, malformed groups and trailing data are rejected. Group size can grow with attribute cardinality, so decoded-page and cache admission limits remain enforced.

Partial memory hits reuse their validated catalog during fallback. Missing sources project summaries/minima directly from the validated directory while building one reusable overview; it is not immediately decompressed again. Failure to build that disposable overview skips admission and still returns the validated catalog. Corrupt cached sources are discarded and rebuilt from canonical R2. Root tombstones/live frequencies stay query-local. Process eviction clears the LRU and can recover it through Cache API; losing both layers restores R2 acquisition. The v2 namespace replaces the previous filter-specific source format without compatibility reads. Canonical R2 root/index/log formats and the projected catalog response remain unchanged.

The 4 MiB L1 term cache has one charged entry per bucket, immutable segment key and header length. Each entry retains dictionaries by canonical term selector and physical eligibility minima by filter selector. Changing only filters reuses the dictionary; changing only terms can reuse eligibility. Query-local references survive concurrent eviction. Missing parts are acquired in separate ordered groups: full projections, dictionaries without filters, or eligibility-only projections with zero terms. Groups run sequentially inside each sixteen-segment window, with up to eight windows concurrent; final catalogs restore input order before live statistics are aggregated. The internal zero-term projection has a current eligibility-only consumer and does not change public text-query validation. Clearing immutable memory also clears these entries, while native/Cache API projections remain disposable shared layers. Global live frequencies are still recomputed against the selected root and its removed frequencies. All segments are prioritized by descending projected score bound and then ascending UTF-16 minimum id. Bounds use cached physical eligibility minima with fresh live statistics; deleting a physical candidate can only loosen this bound. A null minimum proves that no physical document satisfies the predicate and skips ranking, but that segment's dictionary still contributes to namespace-wide frequencies. Tombstones and filters remain exact in the ranker before top-k. No bound-only path acquires a full directory. Candidate ranking and result materialization acquire directories only when needed.

For strong reads, a manifest commit changes the live segment set and tombstones before query evaluation. Edge-eventual reads can observe pre-mutation rows within their explicit snapshot age bound; a minimumSequence barrier requires the acknowledged mutation. Cached old bytes therefore cannot restore removed rows. No purge is needed to keep mutations correct; immutable bytes can remain cached until eviction. Local workerd tests exercise Cache API, memory eviction, namespace separation and mutation reconciliation. Native Workers Cache, regional tiers and request collapsing require deployed evidence because the local emulator does not implement them.

R2 public custom-domain CDN caching, Smart Tiered Cache for public buckets, and Cache Reserve are separate Cloudflare capabilities. They are not enabled by an R2 binding or a `cache.put` call. The bucket remains private; this architecture uses the internal Worker cache path instead of exposing canonical documents through a public bucket domain.

References: [Workers Cache](https://developers.cloudflare.com/workers/cache/), [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/), [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).

Native cache smoke evidence recorded both Workers Cache hits and Cache API hits after clearing the volatile range/directory caches. The authenticated metadata endpoint exposes segment count and the UTF-8 size of the currently Schema-encoded manifest view, plus process-scoped cache counters. Encoded size equals the canonical compact object written by the engine; an empty, uncommitted namespace can have a virtual manifest with no stored object. These are operational diagnostics, not a billing meter. Computing encoded size occurs only on metadata reads, not on ordinary query acquisition. The local gate and executable negative lint probes are documented in the README. SciFact ranking judgments have independent verification in [retrieval quality](quality.md); general performance parity remains unverified.

## Vector metadata lifecycle

Alchemy provisions equality and numeric indexes for each configured field slot, up to five fields and ten native indexes. The runtime stores a SHA-256 digest of Schema-encoded scalar values in each equality slot, avoiding the provider's string truncation and preserving scalar type and null distinctions. Numeric slots retain native float64 values. Pushdown stays below the provider's 2048-byte filter limit and uses its supported bound combinations. The original R2 predicates always run after candidate reconciliation.

Every stack deploy runs the native Command.Exec metadata migration without memoization. It inventories namespace prefixes through the authenticated paginated operator API and rebuilds vectors in batches of at most 100. Rebuild checkpoints store the immutable root view and field layout in R2, and cursors are validated. Resumed pages reconcile revisions, deletion and physical compaction against the current R2 root. A namespace reset or field-layout change rejects the old cursor. Native upserts are deterministic by epoch, document and revision, so page retries preserve identity. Checkpoints remain available for retries for seven days from their R2 upload time, including completed checkpoints. Expired cursors return 410 and require a new snapshot. Vectorize indexing visibility remains eventual.

The deployed metadata migration inventoried seven existing R2 namespaces and resubmitted two existing vectors. The deployment graph references complete native index outputs before supplying the field binding, and the migration references the complete Worker output before consuming its URL. Referencing the stable URL alone allowed migration to start against the previous Worker; the ordered resource references now own that dependency.

## R2 segment collection

`collect` runs under the namespace coordinator semaphore. Each invocation reads the active root, inventories rebuild checkpoints, then visits at most 100 segments using native R2 cursors. The active root and every unexpired checkpoint pin their referenced segments. Checkpoint inventory is bounded to 1,024 objects, 8 MiB per checkpoint, 32 MiB total checkpoint input and 16,384 unique segment references; exceeding either budget fails before deleting any segment. Expired checkpoints can be removed while inventory is built.

An unreferenced segment gets a separate retirement marker with its key, ETag and observation time. Its original upload time does not start the quarantine: a segment may have been live until moments ago. A subsequent collection can delete the segment only after 24 hours with the same ETag and no current pin. Replacement resets the quarantine, a future timestamp resets the observation, and a current pin cancels the marker. Deletion precedes marker removal, making interrupted deletion retries safe. Malformed markers and unavailable checkpoints fail closed. Derived retirement markers do not change the canonical root schema.

Edge text evaluation has a 30-second response deadline after snapshot selection; selection itself requires a snapshot younger than one second. The 24-hour retirement quarantine therefore covers those detached readers. Strong queries and rebuild pages serialize with collection and cannot race a physical deletion. The collector does not delete logs, receipts or old Vectorize epochs. It is an explicit operator operation; automatic scheduled collection and Vectorize epoch reclamation remain outstanding.

## Bounded independent query reads

Text evaluation loads candidate segment dictionaries with at most eight concurrent batch reads, then computes global live document frequencies in manifest order. Within each batch, immutable catalog memory hits are retained and touched independently; only missing ranges enter the internal Terms request. Returned catalogs are merged by original batch position before live frequency aggregation, including when cache admission evicts another query-local hit. Exact segment score bounds are evaluated in batches of at most 64 catalogs, decoding the shared namespace statistics once and constructing each encountered term's BM25 scorer once per batch. The temporary scorer map borrows catalog keys and is dropped with the batch; block maxima and eligible field-length minima remain segment-specific. The returned bound count and finite values are checked before priority sorting. Only competitive segments acquire the full posting directory from the Rust directory already loaded for ranking. Offsets, first/last rows and block counts are absent from the cached score projection. Within each scored segment, requested term spans are grouped in their original order. Coalescing admits at most 16 KiB of additional gaps per group and a combined range of at most 1 MiB; larger individual spans retain their existing segment bound. Up to four grouped ranges are acquired concurrently. The reader validates ordering, gap/size budgets, positive lengths and segment bounds, then passes only the selected subarray slices to Rust in the original block order, preserving the strictly increasing row invariant. Gap bytes are transferred and charged but never decoded as postings. Final hit documents also load with concurrency four and preserve ranking order. Within each Rust segment ranker, exact block bounds are prepared lazily when top-k first fills and reused for subsequent pruning. Block selection remains the original linear first-match lookup and bounds are summed in sorted term order; the cache belongs only to that finish operation. Any-mode candidates retain the union traversal. All/phrase candidates use the shortest posting list as a driver, skip excluded driver rows before alignment and seek other lists with adaptive exponential/binary search. A terminated list ends the intersection. When every list covers every physical document, row positions coincide with their indices; cursors synchronize only after excluded rows cause divergence. Valid candidates retain the original sorted-term score accumulation and repeated-token phrase order. The first four prioritized segments form a sequential prefix so early cutoffs can skip later work. Remaining segments run in windows of at most four, sharing a four-permit limit across directory and posting acquisitions. Each window uses the cutoff from the preceding completed window; its results merge in stable score/ID order before the next window. At most four grouped ranges per segment are acquired together. Four retained rankers and four in-flight reads are per-query limits, not a total Worker memory bound. No query-result caching is introduced. Cold concurrent workerd requests are checked against the strong scorer for identical IDs, revisions and scores.

Query responses expose request-scoped Server-Timing for dictionary acquisition, ranking/posting acquisition and result-document acquisition. Edge responses additionally measure snapshot selection; coordinator and gateway totals are retained. These are elapsed intervals, including I/O, rather than CPU measurements. `tooling/load.ts` records each response's timings alongside its latency samples without deriving per-request statistics from shared counters.

The benchmark bucket's recorded physical location is `enam`. Cloudflare currently lists R2 hints for western/eastern North America, western/eastern Europe, Asia-Pacific and Oceania, and does not list a South America hint. Hints apply at creation and are best effort; a bucket's existing location cannot be relocated by updating its hint. This is a deployment constraint, not proof that geography explains every measured delay. See [R2 data location](https://developers.cloudflare.com/r2/reference/data-location/).

Warm edge namespaces retain decoded snapshots in an isolate-owned LRU before using Cache API. Entries keep their original R2 observation timestamp; neither a memory hit nor Cache API rehydration extends freshness. The cache is capped at 24 MiB of conservative charge, using four times the encoded UTF-8 size per snapshot; oversized snapshots bypass this layer. Namespace and bucket identity stay in the key. Invalid ages and insufficient sequence barriers trigger fresh R2 acquisition. The LRU may retain an expired snapshot with its R2-sourced ETag as a conditional-read candidate; it is never eligible for ranking solely because it remains in memory. A native conditional get confirms an unchanged ETag without a body, then establishes a new observation timestamp measured before that read. Changed content is fetched and fully decoded. Cache API rehydration retains a previously R2-sourced ETag and publication-attempt timestamp only when the validated cached payload matches the prior sequence, byte length and complete bytes. Native [timingSafeEqual](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/#timingsafeequal) compares the equal-length views, including their offsets. Cache response headers never supply origin provenance. A missing origin or different payload still requires a full R2 read on the next refresh. Rehydration keeps the cached frame's own observation timestamp; preserving an ETag never extends that lease. The same age and sequence checks apply after either acquisition path. `edge_snapshot_revalidated` marks foreground conditional-read confirmation, and health counters report body bytes and confirmations. Strong reads never use either snapshot cache. Cache API remains the shared data-center layer. Snapshot responses carry the original observation time and manifest sequence in validated headers, so missing metadata, expired/future ages and insufficient sequences discard the body before JSON decoding. An eligible body still undergoes full Schema validation and the original age/sequence checks. Headers never extend freshness or authorize a stale body. Per-request `edge_snapshot_cache_rejected` marks this early rejection; health counters expose snapshot decodes and header rejections. Immutable segment ranges retain the native Workers Cache regional tiers.

Vector synchronization still processes version-specific deletions, but only submits upserts whose epoch and revision remain live in the canonical R2 root. Superseded jobs are acknowledged without allocating obsolete provider vectors. The indexed-field configuration is decoded once per synchronization operation. This removes unnecessary mutation and storage work; it does not reclaim vectors that an older provider mutation already made visible before the revision changed.

## Bounded Queue batching

Vector consumers receive up to sixteen messages per batch, index consumers up to eight, with a one-second batching window and at most four native consumer invocations. The Worker processes at most four messages concurrently. Namespace Durable Object semaphores retain serialization of canonical mutations. These are separate concurrency limits, not a claim of sixteen-fold throughput.

A validated vector notification drains up to sixteen canonical jobs, rather than only its own sequence. Only a notification still referenced by the canonical root may trigger that drain; duplicate or retired notifications submit zero jobs. Log identity and namespace are checked before dispatch. Upserts and version-specific deletions share bounded buffers across the selected jobs, flushing at 100 entries and committing the root only after all provider submissions succeed. Live revision/epoch checks prevent superseded jobs from allocating provider vectors. Provider failures retain the outbox and replay deterministic identities.

Every queue message owns its acknowledgement or retry, including decode failures and failed binding calls. A malformed message retries without cancelling a healthy sibling. Response bodies are consumed before acknowledging. Dedicated dead-letter queues remain provisioned.

## Query encoding and cache decisions

The original term order, the sorted projection selector, filters and global statistics are each encoded once per text query for their repeated consumers. Each ranker still receives its own tombstones. The candidate array is already sorted after each segment merge, so no duplicate final sort is performed. Exact score bounds, returned rows, snapshot age and authorization remain unchanged.

A twelve-query cold local regression observed thirteen immutable range reads, the same as one query in that fixture; ten isolated repeats also passed after switching to physical bucket identity. That full-query evidence alone did not justify another acquisition owner. A later direct range-boundary test demonstrated duplicate body consumption despite native collapsing; pending-only sharing now addresses that separate cost, as documented above. Native deployment still has cold directory-acquisition tails; local cache efficiency does not establish regional latency guarantees.

Workers KV was evaluated for mutable snapshots and immutable derived data. Its documented propagation and negative-cache delays can exceed sixty seconds, incompatible with this engine's less-than-one-second snapshot contract. Immutable bytes already have native Worker Cache tiers and local Cache API ownership; another KV copy would introduce a read/write path without demonstrated benefit here. R2 remains canonical, with no new stateful dependency. See [KV consistency and caching](https://developers.cloudflare.com/kv/concepts/how-kv-works/) and [Queue batching and retries](https://developers.cloudflare.com/queues/configuration/batching-retries/).

Posting telemetry keeps request-local elapsed intervals for directory/ranker preparation, acquisition windows, Rust block decode and scorer finalization. Server-Timing descriptions include logical spans/bytes, decoded blocks and scored segments. Spans count selected term spans, ranges count grouped acquisitions, and bytes include admitted gaps. These counts include memory/shared acquisition reuse and do not equal R2 origin calls or transfer. Native clocks can remain unchanged during uninterrupted CPU work; zero durations are not CPU measurements.

Query Schema decoders, encoders and namespace/operation guards are created once per isolate. Effect retains the compiled parser on each native adapter; constructing a new JSON Schema and adapter for every segment discards that identity. Request data, validation options and results remain query-local. Two alternating local comparisons over 50,000 documents and 100, 30 and 8 segments checked 2,688 identical responses, including exact scores and sequence barriers. Rare-query medians improved by 8–28%; common-query medians improved by 2–18%. Some filtered/phrase cells regressed by up to 18%, so this is not a uniform latency guarantee or evidence of production improvement.

The native production CPU profiler can identify work that elapsed request timers miss. A ten-second capture under concurrent queries contained Schema compilation and guard construction alongside Effect execution, JSON parsing, cache publication and Rust frames. Source mapping must match the deployed bundle exactly; samples describe one selected isolate and include idle time. They do not establish billed CPU or request percentiles. The corresponding heap capture returned no allocation samples and cannot establish retained or peak memory. See [Cloudflare production profiling](https://developers.cloudflare.com/workers/observability/profiling-in-production/).

Queries with more than four candidate segments may retain conservative score upper bounds in a one-MiB process LRU. Selection identity hashes the complete Schema-encoded ranking input, including text, mode, filters and computed live global statistics; top-k is normalized to one and tombstones are scoped separately. Each entry additionally identifies the physical bucket, immutable segment key, header length and exact tombstone rows. After ranking a segment, its learned upper bound is the maximum of returned scores and the external cutoff used to omit posting pages. Keeping the cutoff is necessary: absent pages can hide scores up to that cutoff. A later lookup takes the minimum of this bound and the ordinary catalog bound, then applies the existing conservative tolerance and ID tie order. Returned rows are always ranked and materialized against the currently acquired canonical manifest; no result rows, root authority or authorization are cached here. Entries are independent of requested top-k, charge key/entry overhead, evict by LRU and disappear on namespace rebuild or process eviction. Missing entries retain the original execution path. Health/metadata expose charged bytes and entry count; these are retained-cache diagnostics rather than peak-memory measurements. This optimization targets repeated selections, not cold-query latency.

A separate one-MiB process LRU retains compact text plans for selections with more than four candidate segments. A plan contains computed global statistics and aligned per-segment eligibility/catalog upper bounds, without term dictionaries, rows or native handles. Its identity hashes Schema-encoded Rust-normalized tokens, mode, filters, current live document/title/body totals and every selected segment's immutable key, header length, tombstones and removed frequencies. Any/all identities sort and deduplicate the normalized tokens; phrase identities retain their order and repetitions. Learned segment maxima use the same normalized text identity. The original request text still reaches the Rust ranker. The physical bucket and namespace/object prefix scope the cache key. No manifest sequence or object-reference shortcut substitutes for this content identity: compaction may change segments without changing sequence, and a document outside selected segments can still change global scoring totals. Current manifest acquisition, authorization and minimumSequence checks precede planning. On a hit, current segment objects receive the retained eligibility/bounds; learned score bounds remain separately scoped to exact scoring inputs. Top-k does not change plan validity. Missing, evicted or oversized plans use the original catalog path. Entry charge includes four times encoded plan length and key length plus entry overhead; namespace rebuild clears the plan entries. This reallocates one MiB from encoded directories while preserving the fifty-two-MiB cache quota sum and does not establish total Worker peak memory. Metadata/health report plan charge, entries and process-local hits.

Completed text plans can recover through the native Cache API after isolate memory is lost. Their key includes the same complete current selection identity plus Cloudflare's native Worker version ID from `CF_VERSION_METADATA`. The version binding is provisioned by Alchemy; no manual engine-version setting or cross-deploy scoring reuse is used. After ranking, each segment's original catalog bound can be tightened with the minimum of that bound and a learned conservative maximum; omitted pages remain covered by the external cutoff. Unranked segments retain their original safe bound. Memory retains the tightened plan, and a new or improved plan is published as a compressed Rust CRC frame with a one-hour cache lifetime. Canonical R2 segments and manifests are unchanged.

Shared-frame admission caps encoded JSON at one MiB and compressed bytes at 256 KiB. Readers bound declared/actual compressed size and the declared inflated length, verify Rust framing/checksum/decompression limits and the concrete SharedTextPlan Schema, then require matching selection identity, Worker version, segment count and current document/title/body totals. Invalid, missing or unavailable cache entries recover through catalog acquisition. Namespace rebuild clears process memory; it can then safely rehydrate an immutable shared plan for unchanged canonical inputs. Tests simulate the same deployed version across fresh workerd instances with a stable native-shaped version fixture; production uses Cloudflare's actual binding. Server-Timing reports request-local plan provenance (`bypass`, `memory`, `shared`, `miss`) and learned-bound hits. Cache publication has a separate put interval and is excluded from the ranking interval. No response rows or authorization are shared through this cache.
