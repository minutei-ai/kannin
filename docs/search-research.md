# Search engine research

Reviewed on 2026-10-19 against Kannin `db1b9fa`. This is an engineering reference for local experiments, not evidence of a Kannin speedup or production parity. Measured results belong in [performance](performance.md); shipped behavior belongs in [architecture](architecture.md) and the [contract comparison](turbopuffer-contracts.md).

## Decisions for Kannin

R2 remains canonical storage; TypeScript/Effect owns the Worker and native bindings; Rust/WASM owns exact lexical search; Vectorize remains the ANN provider. Research does not change strong reads, the bounded-age edge contract, tombstones, live global statistics, corruption checks or cache admission.

1. **Reduce work needed to open a segment.** Audit canonical header parsing, derived-frame construction, decompression and reconstruction before changing the scorer. Quickwit's small opening cache and SlateDB's distinction between decoded blocks and cached bytes reinforce this direction. Kannin already has both encoded and decoded caches; adding another cache is not the first experiment. Trace `SegmentOrigin` in `src/worker.ts`, acquisition/publication in `src/storage.ts`, and directory parsing/compression in `crates/engine/src/segment.rs`.
2. **Count dependent storage rounds.** Draw the actual dependency graph for root, eligibility, corpus statistics, postings and final documents. Fetch independent data in the same bounded wave where its identity is already known. Do not replace a precise read with speculative full-index prefetch. Preserve one captured root and exact namespace-wide statistics.
3. **Keep batches through scoring and filters.** Compare the existing `Search`, posting cursors and filter-mask construction with a bounded window accumulator and bitmap of touched rows. Measure long queries, common terms, large top-k and selective filters. Preserve score accumulation semantics, ties and exhaustive-oracle equality; fewer visited rows alone is not a latency result.
4. **Evaluate a posting-specific codec.** Kannin currently uses 128-row blocks with delta varints and compressed pages. Compare bytes, decode CPU, metadata size and end-to-end reads with a bitpacking candidate before changing block size or persisted format. Preserve positional/phrase behavior, validation and a single explicit format cutover if one is eventually justified.
5. **Evaluate `alyze` separately from performance work.** Its Unicode analyzer is a concrete reuse candidate, including a WASM workspace. Changing tokenization changes indexed terms and ranking: compare Portuguese accents, composed/decomposed Unicode, identifiers, emoji, punctuation, phrases and the quality corpus. Check dependency/bundle cost and an explicit index migration. It is not a drop-in equivalence claim for Kannin's current NFKD normalization.
6. **Measure write amplification and background interference.** Audit small segments, optional artifact PUTs, compaction bytes and queue batches. Group commit is a candidate only with bounded wait/bytes, durable acknowledgements and correct per-request receipts. Cloudflare Queues remains a delivery mechanism; canonical outbox/commit state stays in R2.

These are hypotheses in priority order, not six new frameworks or a promise to implement every mechanism. Run one bounded experiment at a time, reject regressions and remove unsuccessful variants. Local heavy jobs remain serial and below the user-approved 10 GB host budget; this does not enlarge the Worker memory limit.

## What the Turbopuffer material establishes

**Storage and durability.** Its design puts durable state in object storage, uses conditional publication and separates expensive indexing from serving. A successful write is durable before acknowledgement; strong reads also search unindexed writes. Eventual consistency has a different visibility contract. Read the explicit [query consistency parameter](https://turbopuffer.com/docs/query#param-consistency) alongside [guarantees](https://turbopuffer.com/docs/guarantees); do not apply the eventual-mode 128 MiB tail cap to strong queries. The [queue article](https://turbopuffer.com/blog/object-storage-queue) describes indexing notifications, not the canonical write log. Its broker uses group commit and acknowledges after persistence; adopting its single-object queue is not required to retain its lessons.

**Lexical execution.** [FTS v2 postings](https://turbopuffer.com/blog/fts-v2-postings) decouples lexical blocks from vector clusters, targeting about 256 postings with split/merge boundaries of 128–512. It uses specialized integer compression. [Vectorized MAXSCORE](https://turbopuffer.com/blog/fts-v2-maxscore) amortizes iterator work and processes consecutive postings before changing terms. The [Rust/SIMD investigation](https://turbopuffer.com/blog/zero-cost) shows why a recursive element-at-a-time iterator can inhibit vectorization even when the abstraction itself compiles efficiently. These are reasons to inspect batch shape and generated WASM, not to ban iterators or import native AVX code.

**Current direction.** The [v3 announcement](https://turbopuffer.com/blog/rip-vector-database) describes moving away from vector-primary storage to reduce document duplication, relocation and query-layout constraints. The [development log](https://turbopuffer.com/v3) reports keeping postings batched through scoring, page-wise filter evaluation with compute pushdown, and overlapping corpus-statistic reads with posting/filter data. Its published comparison remains a work-in-progress against production v2 with mixed results. Copying v3 wholesale would neither establish speed nor fit this project's scope.

**Quality.** [Native filtering](https://turbopuffer.com/blog/native-filtering) makes the filter participate in ANN candidate selection; filtering an already-truncated candidate list can lose matches. [Continuous recall measurement](https://turbopuffer.com/blog/continuous-recall) compares sampled ANN queries with exact search. For Kannin, Vectorize needs real filtered recall tests against an authorized exact corpus, including stale/deleted revisions and selective predicates. Local vector fixtures establish protocol behavior, not provider recall. BM25 needs separate relevance evaluation and an exhaustive scoring oracle.

**Retrieval pipeline.** [Native embedding](https://turbopuffer.com/blog/native-embedding) overlaps independent metadata acquisition with embedding work. [Attribute ranking](https://turbopuffer.com/blog/rank-by-attribute) folds bounded non-text contributions into first-stage ranking. Both are useful dependency/planning lessons; neither justifies silently adding embedding inference, recency boosts or reranking to Kannin's existing query contract.

**Operations.** The [control-plane article](https://turbopuffer.com/blog/control-plane) separates recoverable operational state machines from serving and discusses staged rollouts. Its Kubernetes/etcd/MySQL control plane is not its canonical search store. It is not a template for introducing those systems into this Worker.

## Benchmark discipline

The [performance page](https://turbopuffer.com/docs/performance) currently labels strongly consistent BM25 over 1M documents/~300 MB with warm p50/p90/p99 of 13/18/29 ms and cold 316/381/559 ms. These are provider-published observations, not a numerical SLA or measurements of Kannin. Its vector example is a different workload. The architecture page's short vector-size caption differs from the performance page, so retain the source and full workload description rather than treating every repeated headline as the same benchmark.

The pinned [official benchmark definitions](https://github.com/turbopuffer/tpuf-benchmark/tree/6a1d2cf934cfbc570352e54a91716e74bae55466/benchmarks/website) use 10M MS MARCO documents for their FTS hot/cold workloads at 8 QPS for 30 minutes. Hot waits for full cache residency; cold disables cache. The v3 page describes its own 10-minute comparison. These experiments are distinct from the 1M-document performance-page example. Do not run their remote seeding scripts or use internal cache-control parameters as assumed public API contracts.

For a future comparison, record dataset/version/hash, document sizes, analyzer, field weights, query distribution, filters/selectivity, top-k, update/tombstone state, consistency, indexing backlog, client/provider region, concurrency and cache state. [BM25 scaling](https://turbopuffer.com/blog/bm25-latency-musings) shows why adding terms or changing top-k can reorder which queries are fastest. Separate fresh-isolate cold, all-derived-cache-absent cold, partial cache and warm runs. Capture complete result equality, quality, CPU, wall time, bytes, storage operations, queue work and peak memory; retain unsuccessful runs and enough samples for any reported percentile.

Turbopuffer's warm tier uses NVMe and RAM, with routing that favors cache locality. Workers' [128 MB per-isolate limit](https://developers.cloudflare.com/workers/platform/limits/#memory) includes WASM and concurrent requests. [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) is data-center-local and `cache.put` does not provide tiered caching. It is not an application-owned NVMe disk. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/) and [conditional operations](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) must be evaluated at their native contracts, separately from cached responses. Serverless service delivery does not imply every vendor implements one ephemeral Worker per request.

The [pricing page](https://turbopuffer.com/pricing) describes commercial usage and commitments. A cost comparison must include R2 retained data, GET/PUT/list amplification, Worker CPU, coordination, optional cache artifacts, queues and Vectorize. No price advantage follows from cheap bucket storage alone. Do not compare loopback MinIO latency, native mmap throughput or a cached microbenchmark with a regional service's end-to-end results.
